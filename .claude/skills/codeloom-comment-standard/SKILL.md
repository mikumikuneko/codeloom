# codeloom 的注释判据

写够到保住**契约**，然后删掉推理过程、重复和装饰。契约 = 调用方 / 被调方 / 实现方 / 生产者 / 消费者所依赖的**义务、不变量、前置与后置条件、兼容承诺**。

注释只写代码表达不了的非显然契约或理由，**不重述代码已经说明的事**。

这是判据，不是脚本：下面每一条都要你自己判断该不该套。

## 范围与排除

适用：`codeloom-*/src/{main,test}/java` 的全部注释、`frontend/src` 里的注释，以及配置和 SQL 里的注释（`docs/sql/schema.sql`、`application*.yml`）—— 它们同样在讲理由，同样会腐烂。

不适用：字符串字面量。**给模型看的工具描述、给用户看的报错文案、`@DisplayName` 里的用例名、断言里的文本 —— 那些都是行为，不是注释，一个字都不许动。** 模型可见文本见 `codeloom-prompt-standard`，界面文案见 `codeloom-ui-standard`。

先确认 scope 和模式：**review 只报不改，edit 才动文件**。scope 不清就问，不默认全仓；改之前先读代码、测试和相关决策，以当前代码为准，不凭记忆。

## 完整命题

删之前先把这段话里的命题逐条列出来 —— 主体与动作、条件/时机/顺序、情态（必须/可以/绝不）、**否定式保证与例外**、归属、副作用、失败模式、后果。删完形容词、重复、叙述之后，**每条事实从句都必须活下来**。

**字数变少本身不是改进。** 类注释以 2–6 行为目标，但不是配额；多条契约需要更多行时保留，harness 自己的复杂类注释也不短。

改过头有四种，见到就退回：把**义务**说成优点（"必须这样" → "这样更好"）、把**假设**说成事实（"如果 X 就会 Y" → "X 会 Y"）、为了短**删掉一条真事实**、丢掉**证据来源**（"实测过""provider 报的"这种词是承重的）。

## 按位置的覆盖要求

**这是补充，不是单向删减**：代码、类型、结构没能说清的契约，缺了就补（已经显然的不补 —— 那只是复述代码）。

- **公开 API**：调用方看得见的返回值差异、抛什么、副作用、归属、时机、取消、持久性；每个参数写 `@param`，非 void 写 `@return`，非显然的运行时失败写 `@throws`。
- **内部注释**：只用于跨文件的结构和显然复杂的局部 —— 不变量、竞态顺序、归属、安全边界、意外的失败行为。删掉控制流的叙述和对代码的重述。
- **类注释**：角色、依赖、职责、非显然的架构选择。不要逐段预告下面的实现。
- **测试**：只解释非显然的测试设计 —— 为什么需要这个 fixture、为什么这条断言要观察外部结果而不是模型自己的报告、为什么要适配某个平台、为什么必须走真实入口。删掉流程走查和清单式罗列。
- **配置和 SQL**：只写非显然的接线、读取顺序、权限/安全边界、回放/兼容行为，以及容易误用的地方；不复述配置项本身。

## Java 与 Markdown 的形式

Java 注释不是 Markdown，TypeScript/JSDoc 的排版不能直接照搬：

- **加粗和反引号不生效**：`**` 在 Java 注释里是普通字符，反引号也不会变成代码。代码写 `{@code ...}`，类型/成员写 `{@link ...}`。
- **段落用 `<p>`**：Javadoc 里空行不会产生新段落；多段注释的后续段落以 `* <p>` 开头。`@param` / `@return` / `@throws` 的说明内部不要再塞 `<p>`。
- **不用标题和装饰性强调**：不要用 `<h2>` 分节；不要用 `<strong>` / `<b>` / `**` 强调。需要强调就靠词句本身：必须、绝不、只、唯一、尚未。
- **代码块只在真是代码块时用 `<pre>`**：命令、输入输出对照、路径映射可以用；不要拿它排版普通散文。
- **列表要真是并列项**：只有内容确实是离散清单时才用 `<ul>` / `<li>`；能用一段话讲清就不要拆成清单。
- **尖括号不是占位符**：不要写 `<sha>` / `<ownerId>` / `<path>` 这类占位；路径和命令模板用文字或全大写占位符（`SHA`、`PATH`）。Javadoc 结构标签（`<p>`）是另一回事。
- **决策路径不是链接**：`{@code docs/decisions/...}` 只是文本，IDE 通常不可点；写决策文件名便于搜索，不要声称它可以点击。指向 Java 元素用 `{@link}`，不要拿它指文件。
- **只链可访问的 Java 元素**：跨类 `{@link}` 到 private / package-private 成员是无效链接；未导入的简单类型也可能解析不了。改完扫一遍所有 `{@link}`，或至少在 IDEA 里确认没有红。

## 理由放在哪

- **本地契约必须留在注释里**：行为、失败、时机、所有权、副作用、默认值、不变量、否定式保证。读者在 IDE 里看不到决策文档时，这些事实仍要完整。
- **扩展理由放决策记录**：为什么选这条路、否决了谁、踩坑史、长权衡，放进 `docs/decisions/`；注释压成一句结论 + `{@code docs/decisions/...}` 或决策文件名。
- **有现成决策才链接**：先搜 `docs/decisions/`；没有对应决策时保留一句必要的非显然理由，不为了链接新造一篇。
- **一处解释一处家**：同一个理由只讲一处；兄弟分支、多个调用点、测试 fixture 指过去，不各写一遍。找法是搜一句特征话，而不是只搜文件名。

## 删这几类

- **过程叙事**（"从前是 X，踩了这个坑，于是改成 Y"）→ 压成"结论 + 后果"。一句，不是一段。修好的回归写成**反事实现在时**（"少了 `min-h-0`，内容会把容器撑开"）—— 比"从前…现在…"短，而且不会过期。
- **无关展开**（在这里解释另一个类、另一件事的行为）→ 删掉，或压成一个指向它的短句。
- **重复**：同一个理由在第二处又写一遍。一处讲清，其余指过去。找法是搜一句特征话（同一句被搜出两次以上）；同一个理由在一组兄弟分支旁各写一遍，是最常见的一种。
- **会腐烂的状态和清单**："目前只有 X""暂时只支持 X""将来会 X"，以及把代码里的目录抄一份进来（有哪些工具、哪些事件）—— 权威在代码里，抄进注释就是等着它过期，而且过期了没人会想起来改。
- **比喻**（"闸/门/环/地基/谎/承重/死结/脚下的地"）—— 它们不是禁词，用之前先复核：说"环"可能真在说一个环（上下文环），说"门"可能真是一个准入点。能换成更精确的说法时再换，不要为了"朴素"换掉有明确定义的领域词。

## 保留这几类

- **否定式保证**（"它不带 X""别这么做"）—— 省略会让下一个人把删掉的东西加回来。
- **陷阱清单**（"四个容易写错的地方""残留的洞"）—— 省略会导致误用。
- **可搜索的机制名**：wire 字段名（`reasoning_content`）、HTTP 头名（`Retry-After`）、工具名、环境变量名、事件名。
- **有意义的情态**：必须 / 可以 / 绝不 / 只 / 唯一 / 尚未 / 以后。靠词保留，不靠加粗或 HTML。

## 用词

同一个概念**全仓只用一个词**。已经定过的两对：

- **账号** = 登录用的 / **用户名** = 界面上显示的那个（和日常中文习惯相反）
- **服务端** = 我们这一侧 / **服务商** = 提供模型调用的外部官方

发现两个词在指同一件事，先定哪个对（拿代码和产品形态判），再**全仓搜一遍一起改** —— 只改一处，下一个读的人会以为它们是两回事。

## 引用外部项目

只留**项目名 + 公开可查的原话（报错原文、README 原句）+ 行为描述**；用户可见的工具名（`Write`、`Edit`、`Bash`）可以留。

**删掉**：文件路径、内部方法名/常量名/事件名/类型名、代码片段、英文源码注释的引用 —— 那些对读者是死链接。判据一句话：**读者能不能自己查证。**

**点不出名的归属就删掉那半句**，保留事实本身。"参考实现"三个字后面必须跟着是哪一家（本项目有两个参考实现：Claude Code、deepseek-harness）。

## 工作流

1. 确认 scope 和模式；review 只报告，edit 才落文件。
2. 读代码、测试、相关决策，判定当前真实行为；注释与代码冲突时先核代码，再改注释。
3. 把候选段落的命题逐条列出，分类为 keep / add / trim / restructure / defer；不要为了删而删。
4. 只改注释；不碰字符串、`@DisplayName`、断言文本、模型可见文案和界面文案。
5. 修一类问题就按同一特征搜全局：同一句特征话、同一种 HTML/加粗/占位写法、同一种读改写顺序。能一起修的一起修；范围外或需要改行为的，列清单说明原因，不擅自扩大改动。
6. 改完做窄检查：`git diff` 过滤非注释行、编译/测试（注释不改行为，但不能把代码改坏）、决策路径存在、确认没有 `<h2>` / `<strong>` / `**` / `<...>` 占位；注释不能被当成行为证据，跑不了的就说跑不了。

## 边界情况

只有当两个版本都满足"完整命题"、而且上面的判据分不出高下时，才算边界情况 —— 那种时候给两三个选项 + 推荐，再等人点头。

**一个"保住命题"的改写不是边界情况**，直接改。

## 判例

**压叙事**：原句「写这条注释时刚撞上过，测试里订阅者收到的 seq 是 [.., 600, 602, 601, ..]」→「（实测出现过 601 排在 602 之后）」。自述踩坑史去掉，"默认执行器会乱序"这个契约留下。

**修说错话**：注释说「截断点靠 sha 定位」，而代码与相邻事件类都写着定位用的是**事件序号**（sha 会重复 —— 一轮什么都没改时提交返回的还是上一个 HEAD）。这类比措辞问题重要得多：改措辞只是不好读，内容错会把人带沟里。见到与代码不符的注释，先核代码，再改注释。

**定术语**：「服务端」在同一个仓库里既指我们这一侧（"我们是服务端"）又指模型官方（"服务端让我们等多久"）—— 定成 **服务端=我们 / 服务商=模型官方**，再全仓搜一遍一起改（改的时候一个一个看：指模型的那 7 处改掉，指别的面的那 20 处别动）。

**去抽象**：「已经折到哪一条」「增量折不出来」—— "折"是内部的词，读的人卡在这儿。换成"投影已经处理过的最后一条事件""靠'只接着处理新到的事件'补不上"。

**压缩过度**：把"必须在同一事务里、失败会回滚、否则事件和行对不上"压成"原子保存"，事实就没了；宁可多一句，不要丢条件、失败模式和后果。

**Java 形式**：把 `<h2>为什么…</h2>` 改成普通段落；多段之间用 `* <p>`；命令里的 `<sha>` 改成 `SHA`；决策路径写成可搜索的文件名，不要写成 `{@link}`。

**这一节不是死的**：每拍板一个判据分不出的 case，就把两版和结论写进来 —— 去掉"谁在什么时候说的"，只留怎么判。
