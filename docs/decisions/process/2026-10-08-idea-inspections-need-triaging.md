# 决策：IDE 的检查能跑，但它报的红要逐条回源码核

## 是什么问题

IDE 里那一堆"黄红"能不能当一份待修清单直接用？

## 定了什么

能跑（IDE 装目录下有个命令行入口，跑的是和界面里同一套引擎，输出是"一个检查一个 XML"），但报告要**逐条回源码核** —— 它当"提示"用，不当"清单"用。

实测证伪过的：一整片"未使用"是假的（一个 service 的五个字段和五个方法形参全被报成"从未使用"，其实都在用）；17 条"引用了 UMD 全局"是假的（真跑一次带 `-p` 的 `tsc` 是 **0 错**）；"忽略返回值"那条，代码里就写着为什么可以忽略。

真抓到的也有：断链的 `{@link}`（没 import 的类型，校验命令直接就报了 reference not found）、未使用的 import、一个死分支。

## 还考虑过什么，为什么没选

- **照单全改**：会改坏正常代码（"未使用"那一族整片是假的）。
- **完全不用它**：它确实抓到了我们自己的检查没覆盖的东西 —— 而且是**测试源**里的问题（`javadoc` 那条命令从来不跑测试源）。
- **只看数量**：数量最大的两族（"未使用"和"拼写"）恰好最不可信；有信号的是那些小的。

## 代价与换来的

- 每次要人工过一遍；跑之前还得把 IDE 关掉（同一个配置目录不允许起第二个实例），而且**它会写你的 IDE 配置** —— 有一次把编辑器配色从深色写成了白底，所以跑之前先备份配置目录。
- 运行命令的退出码**不可信**（实测三次都是 0，其中两次什么都没产出），判据只能是"输出目录里有没有东西"。
- 换来的是：多了一个能查出"断链引用"这类问题的渠道，用法和我们"断言要实测"是同一条纪律 —— 它说的每一条都要回源码看一眼。
