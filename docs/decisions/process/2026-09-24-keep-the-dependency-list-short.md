# 决策：依赖列表尽量短，能不引就不引

## 是什么问题

这个项目要引哪些现成东西？每引一个都要问：它替我们删掉了多少自己写的代码，代价是什么。

## 定了什么

不引 Lombok、不引数据库迁移工具（Flyway/Liquibase，也不让 `spring.sql.init` 自动建表）、不引 AI 框架、不用 OkHttp、不引 JSON Schema 校验库 —— HTTP 客户端用 JDK 自带的 `HttpClient`，参数校验自己写（`ArgumentValidator`）。

## 还考虑过什么，为什么没选

- **Lombok**：省下的是几个 getter 和一个日志字段，换来的是编译期处理器、一份编译器配置、以及长期的 JDK 升级跟进责任 —— 这笔账不划算。而且 JDK 21 的 record 已经吃掉了它大部分价值。
- **Flyway / Liquibase**：表结构在这个项目里是**一次性设计产物**，不是持续演进的迁移史；手工执行反而让"表长什么样"能被完整讲一遍。代价是加列要自己补 `ALTER`。
- **`spring.sql.init`（启动自动建表）**：它只能幂等地 `CREATE`，做不了 `ALTER`；而且"文件里写什么、库里执行什么"会失去一一对应 —— 手工执行至少不会骗你。
- **AI 框架**（Spring AI / LangChain4j 这一类）：这个项目的价值就在于自己搭 —— 用框架等于把要展示的东西外包出去。模型调用、工具循环、上下文装配都是我们自己写的，换过一家 provider 也只是适配层的事。
- **OkHttp**：它的优势在"高并发短请求"，而我们所有时间都花在等模型上，HTTP 层不是瓶颈；引它还会连带拉进 Kotlin stdlib 和 Okio。
- **JSON Schema 校验库**：它的报错是英文，也没有"给模型自修的那句话" —— 而那句中文报错正是 `ArgumentValidator` 存在的理由。

## 代价与换来的

- 这些活都是自己写：参数校验、重试、流式解析、SQL 映射。
- **没有迁移工具是目前最弱的一环**：`schema.sql` 手工执行，加列靠人记得补 `ALTER`；"事件 payload 的格式版本"这件事一直没有机制兜着。（这条是明确记下来的缺口，不是"还没想到"。）
- 换来的是：依赖树短、升级面小、每一处行为都能指出是哪段代码做的 —— 面试时也讲得清。
- OkHttp 那条再补一句它真正的坑（不只是"多带 Kotlin"）：它那四种分开的超时里，**读超时指的是"两次读到字节之间的间隔"** —— 流式响应里模型"想"十几秒不出字，就会被它掐断。这类默认值对短请求是对的，对我们的场景是个陷阱。

## 什么情况下该重新考虑

真需要"持续演进的表结构"时（比如生产环境已经有不能动的数据），就该把迁移工具引进来 —— 那时它的成本才真的换来了东西。
