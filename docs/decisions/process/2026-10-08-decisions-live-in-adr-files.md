# 决策：决策理由放 `docs/decisions/`，只留一条形态

## 是什么问题

那些"跨文件、有备选、以后有人会问为什么不那样"的理由写在哪？代码注释装不下它们（注释是"这段代码为什么这么写"），对话更留不住（换个会话就没了，而且面试官看不到）。

## 定了什么

`docs/decisions/`：一篇一个决策，文件名是**日期 + class + 短标题**，正文四段（是什么问题 / 定了什么 / 还考虑过什么，为什么没选 / 代价与换来的），可选一段"什么情况下该重新考虑"。

**只留这一条形态**：不做状态目录，不做双语三件套，不做格式校验脚本，不做归档冻结。规矩写在同目录的 `README.md` 里（原地改事实不追加变更历史；不是改写决策的许可；先搜再写；理由用自己的话总结）。

## 还考虑过什么，为什么没选

- **照搬"按状态分目录（提了没做/已落地/被否决/冻结）+ 每篇中英加 sidecar + 脚本 gate"那套**：它成立的前提是**写的人多、周期长、有机器校验**。我们一条都不占：一个作者、零提交、没有 CI。更具体地说，状态一旦住在目录里，每变一次就要挪文件、改正文时态 —— 而"要手工同步的状态"正是我们注释标准里专门删掉的那一类。
- **按 class 分目录**：class 写进文件名就够了；分了目录，重分类就要挪文件。
- **只在代码里写注释**：局部理由够用，跨文件的不行 —— 一条决策会牵涉六七个类，注释里各写一半，读的人拼不起来。
- **不做这件事**：那些理由现在散在注释、三份标准、和我的记忆里 —— 正是"同一事实多个家"。

## 代价与换来的

- 没有机器校验格式，全靠自觉；状态（提了没做、被否决）不在这里表达 —— 未做的留在对话与待办里，被否决的写进每篇第三段。
- 换来的是：决策理由有了一个**能搜、能被读、不跟着代码走**的家；而最值钱的那一段（击败备选的那条理由）在每篇里是必填的。
