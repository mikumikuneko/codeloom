# 决策：给前端的纯投影引一个测试运行器（vitest）

## 是什么问题

前端从建起来到现在**没有一个测试运行器**：`package.json` 的 scripts 只有 dev / build / lint / preview，全仓没有一个 `*.test.*`。验证界面靠"看屏幕"（`testing/2026-10-05-look-at-the-screen`），那条一直有效。

但它盖不住一类东西：**出过真 bug 的只有那批纯投影** —— 折事件流的 `sessionStream`、文本 diff、unified diff 解析、markdown 的增量切分。它们的失效方式都是"折到某个分支上不对"（被拒绝的调用一直闪、回滚退错地方、批准挂起时冒出用量行、这一轮在不在跑判错），而**要看见那些分支，得先跑出一整套真实交互**（挂起等人批、拒绝、中断、回滚、批准续跑）—— 截图能到，成本是每次都要起应用、造状态、按时间点抓住那一瞬。

这一轮里我自己在那批模块上踩了两次（一次判据写错、一次 `running` 恒假），两次都是靠**临时探针**发现的。而探针躺在临时目录里 —— **下一次改动不会有人再写一遍**。

## 定了什么

引 **vitest**：

- `npm test` = `vitest run`；`npm run test:watch` = `vitest`。
- 测试放在**被测模块旁边**（`src/lib/sessionStream.test.ts` 这种），走 vitest 的默认匹配，没有额外配置。
- `@/` 别名不用管 —— vitest 复用现有的 vite 配置解析它。
- 先只给**纯模块**写，而且先写**出过 bug 的那四个**（`sessionStream` / `textDiff` / `unifiedDiff` / `streamingMarkdown`）。`useXxx` 那些 hook 不在这一批：它们要 DOM 环境，是另一件事。
- 测试在 `tsc -b` 的路径上（它们在 `src/` 下），所以写错类型会让 `npm run build` 红 —— 那是想要的。

## 还考虑过什么，为什么没选

- **不引，继续"截图 + 一次性探针"**：探针是一次性的，而那批契约是**长期的**；截图那条路每次都要造一遍真实交互，人不会一直造。
- **`node:test`**（Node 24 能直接跑 `.ts`，零依赖，这条和"依赖要短"最合）：**实测拦住**它的是别名 —— `import('./src/lib/sessionStream.ts')` 直接 `ERR_MODULE_NOT_FOUND`（它不认 tsconfig 的 `paths`，而 `--experimental-paths` 在 Node 24.18 上根本不存在）。要么写一个约十五行的解析钩子，要么把全仓的 `@/` 改成相对路径。**没选**的理由是第一条：那个钩子是 vite 那份解析的**孪生体**，两者迟早不一致，而那种不一致的样子是"测试全绿、应用还是坏的" —— 测试最不该有的失效方式。
- **按覆盖率给整个 `lib/` 铺开**：测试的价值是钉住**契约**，不是覆盖率数字。而那几条契约**注释里已经写好了**（"被拒的调用不能一直闪"、"回滚按 seq 截断"、"没有改动时一行都不裁"、"最后一行没写完这件事只能回到原始正文上判"）。
- **给 hook 和组件也写**：那要 jsdom 和一个渲染环境，判据也变成"界面长什么样" —— 那一侧仍然是截图的地盘。

参考实现那一侧的判据：只有 deepseek-harness 能查（Claude Code 那份是个 `src/` 转储，没有 `package.json`、没有测试文件、没有 CI，**不能据此说它没有测试**）。而 deepseek-harness 在这四类模块上**恰好都用了 vitest**：事件流折叠、markdown 增量切分、文本 diff、unified diff 各有一份 spec（它 `packages/client` 下一共 580 个 spec），而且它明写着一条原则：纯逻辑那一层"**没有 React、没有 DOM、没有宿主概念**"。

## 代价与换来的

- 代价：dev 依赖长一截（不进产物）；多一条要跟的命令。
- 代价：测试和被测代码**放一起**，`src/lib` 目录不再只有实现。这是刻意的 —— 找得到、不会各放一处慢慢走样。
- 换来：那四个模块的契约第一次有东西在跑，而且**边界不用起应用就能钉**（拒绝、中断、回滚、批准续跑、多文件 diff 的行号、超规模时退化成全删全加）。
- **这一篇不推翻"看屏幕"**：那一条管的是界面（布局、空态、颜色、字号、反馈落在哪一栏），这一篇管纯函数的分支。两边各管一段，谁也不替谁。

## 什么情况下该重新考虑

- 哪天 vitest 成了升级负担（大版本破坏性变更、拖着不升），可以退回 `node:test` + 一个解析钩子：测试本身换个运行器是机械的（断言用的是 `expect`），而被钉住的那些契约一条都不用重想。
- 哪天要测 hook 或组件（要 jsdom、要渲染），那是**另一条决策** —— 现在这四条不由它兜着。
