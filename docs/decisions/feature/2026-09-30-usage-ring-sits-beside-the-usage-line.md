# 决策：上下文环是只读的旁证，不落事件、不变色

## 是什么问题

界面上要不要显示"上下文用了多少"？怎么显示？推理用的 token 要不要也显示？

## 定了什么

- 上下文占用**画成一个环**，放在用量那一行旁边；
- **走只读接口取**，**不落成事件**；
- **环满不变色**；"上下文"三个字不省；**没有读数就不画**（不画一个空环）；
- **推理 token 只记库、界面不显示**。

## 还考虑过什么，为什么没选

- **把上下文读数落成事件**（`ContextMeasured` 之类）：环是"轮初的量"，而用量是"轮末结算的" —— 两者节拍不同，硬塞进同一份结算里会让两边都说不清；而且这是**展示信息**，不是事实。
- **推理 token 也显示**：用户明确选了不显示（那个数对"我还能聊多久"没有指导意义）。
- **环满了变色**（比如变红）：那会把"红"这个信号白白用掉 —— 到真正需要警示的时候（比如压缩即将发生）就没有更强的表达了。
- **读数缺失时画一个空环**：零读数的环和"真的用了 0%"长得一样，那是句假话。

## 代价与换来的

- 一个只读接口 + 前端一个环组件；读数缺失时那一行会少一块（而不是显示一个假值）。
- 换来的是：展示与实际节拍对得上（环是轮初、用量是轮末），警报信号留给真正该报警的地方。
