# 决策：正在跑的时候发消息，收下排队，不回 Busy

## 是什么问题

一轮正在跑，用户又打了一句（或者另一个人的 agent 捎来一句话）。把它拒掉让人自己重试？还是收下来等这一轮结束？

## 定了什么

**收下、排队、并且立刻在界面上以"灰显回声"显示自己刚发的那句**（否则用户会以为没发出去）。别人捎来的话也是同一件事，只是它多一个来源字段 —— 落成 `AgentNoteDelivered` 事件，让"谁捎的"成为事实而不是隐式信息。

投递点在**轮末**，那时这一轮还持有租约、还在写事件。队列放在 Redis 的两个 list 里：先原子地把 queue 里的每一条挪进 pending（`RPOPLPUSH`，一条一动），再读 pending（**不删**），落库成功之后才 ack 删 —— 所以"上次崩在中间、还没确认"的那些不会丢，它们本来就该排在前面。读到一条解不出来的坏数据**当场丢掉而不是抛**：否则这条会话再也收不到任何留言。

## 还考虑过什么，为什么没选

- **直接回 409 / Busy 让人自己重试**：那是把自己的复杂度推给用户 —— 他刚打完的字白打了，还要自己判断"什么时候可以再发"。前端体验上也说不通：既然能显示"正在跑"，就能顺手把话收下。
- **审批挂起的时候拦住不让发**（我一开始做的就是"拦住"）：方向反了。那种情况下这一轮并没有在跑，它只是挂着等人 —— 该做的是排队，而不是把门关得更死。
- **中途投递**（不等轮末，插进去让模型马上看到）：那要处理"模型已经读过的上下文变了"（前缀缓存、工具结果的对应关系都会动），风险比收益大。先做保守版，等稳定了再说。

## 代价与换来的

- 留言的可见性有延迟：要等这一轮结束才会到模型手里。
- 一个已知的洞：同一棵树上另一条会话占着租约时，发给这条的话没人来叫醒它 —— 这条取舍先记着，没解。
- 换来的是：用户的输入一次都不丢，且"我在跑的时候你还能说话"这件事在界面上是看得见的（灰显回声）。
- **两个已知的洞，如实记着**：① 同一个人的两条会话共用一棵树，而唤醒只扫"正在跑的那条会话" —— 发给另一条会话的排队消息没人叫醒它（修法是在放开租约的**同一个** `finally` 里唤醒；代价是唤醒就地下跑，同一棵树的总墙钟翻倍，要挪线程池才能摊平）。② 队列只在内存里（Redis 的两个 list），**重启即丢**。
