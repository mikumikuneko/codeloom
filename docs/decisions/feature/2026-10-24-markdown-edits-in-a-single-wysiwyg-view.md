# 决策：Markdown 在同一张视图里就地编辑

## 是什么问题

中栏既要看 Markdown 成稿，也要改它。只读渲染和可编辑源码是两张皮：切过去是一整篇源码，改完再切回来；分开两栏又等于同时维护两套排版。要的是 Typora 那样——打开是成稿，点某一处就在原地露出那一处的记号。

## 定了什么

Markdown 和代码共用 `CodeEditor`。`markdownLivePreview` 扩展在同一张 CodeMirror 视图上按语法树加装饰：光标或选区覆盖的行保留源码（`###`、`**`、`[]()`），其余行用 `Decoration.replace` 藏掉记号并套上标题、粗体、行内代码、链接、引用、列表、代码块的样式；编辑器没有焦点时一行都不露，整篇按成稿铺开。

Markdown 不显示行号。保存仍是自动保存，写前用 `baseContent` 比对磁盘，冲突时要求重新读取。表格和图片不渲染，保持源码：前者要把管道符重排成网格，后者要处理尺寸和加载失败。

## 还考虑过什么，为什么没选

**渲染视图点一下切成整篇源码。** 点开是成稿，但一编辑整篇变成源码，看不到其他部分的渲染结果，也不是"写一行、下一行就渲染"。

**源码和实时预览左右分栏。** 等于把两套排版并排放，屏幕一分为二，每边都窄；而且是 IDEA 的预览方式，不是 Typora 的原地编辑。用户明确否决过。

**引入 WYSIWYG 编辑器（Milkdown、Tiptap 一类）。** 要在 Markdown 和富文本之间做双向映射，映射不精确时保存回来的源码会被改写；还会把撤销栈、自动保存、语法高亮从现有 CodeMirror 上拆走，换一套新的。现有编辑器已经能改、能存、能撤销，缺的只是显示层。

## 代价与换来的

装饰只按当前视口计算，滚动时要重建；换来的是大文件不必每敲一个字遍历整棵树。

被藏住的记号被声明为原子区间，光标不会落进看不见的字符中间，但点到标题、链接的左边缘时定位会退到记号边界。

自写的装饰只覆盖常用的 CommonMark 与 GFM 子集：表格、图片、Setext 标题仍是源码；新增语法要吃渲染，得同时补装饰规则。

## 什么情况下该重新考虑

需要渲染表格、图片，或出现了 CodeMirror 装饰解释不了的块级排版时，再评估是否换成独立的 WYSIWYG 编辑器。
