# 决策：前端选 Tailwind + shadcn + Zustand；反馈就地给，不引 toast

## 是什么问题

前端的组件、状态、反馈这三件事怎么做？还有：两个人看同一场会话的那个页面，要不要单独做一套"观战视图"？

## 定了什么

- **样式与组件**：Tailwind + shadcn（组件是**源码拷进项目**的那种，不是依赖）。
- **状态**：Zustand —— 这个前端的核心就是"订阅事件流 + 把增量事件并进状态"，那是高频写入，用 Context + useReducer 会全树重渲染。
- **反馈**：**就地通知**，不引全局 toast 原语 —— 反馈要落在用户正在看的那一栏。
- **观战**：复用同一个会话页（后端已经把"不能驱动别人的会话"卡死了，界面上不需要第二套视图）。
- **"谁在跑"**：轮询就够 —— 对方正在干活这件事**不需要秒级精度**。

## 还考虑过什么，为什么没选

- **Ant Design / MUI 那类组件库**：设计语言很强，做出来一眼就是"某某后台"，而我们想让它像这个东西自己。
- **Redux Toolkit**：这个前端没有那么多要长期共享的复杂状态，Zustand 的代价小得多。
- **单独做一个观战视图**（甚至并排双屏）：多一套视图等于把同样的渲染逻辑写两遍；并排两个半宽的面板，每个都窄到看不清工具输出 —— 看着诱人，其实是反效果。
- **全局 toast**：我们没有那个原语，而且是**故意**不用 —— 提示飘在角落，用户刚点的那个地方却没有任何变化。
- **给每个会话都订阅 SSE 来显示"谁在跑"**：那要维护 N 条长连接，而这件事的精度要求只是"大概知道"。

## 代价与换来的

- shadcn 的组件在项目里，升级要自己合；观战没有专门的视图，所以两个人在同一个页面上要靠状态区分谁是谁。
- 换来的是：界面一致、状态更新便宜、反馈落在发生的地方。
- **CORS 一行都不配**：开发时靠 Vite 的 dev proxy（浏览器看到的是同源），构建产物也同源 —— 所以"跨源"这件事在这个项目里根本不发生。它曾经被列成"前端开工的硬前置"，后来收回了：把"跨源"和"必须配 CORS"划等号，是自己给自己加的一步。
