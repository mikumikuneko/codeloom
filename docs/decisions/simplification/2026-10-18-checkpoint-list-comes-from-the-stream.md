# 决策：回滚点列表只从事件流读，不再单开一个接口

## 是什么问题

"这条会话有哪些可以退回去的位置"一度有两个来源：`GET /api/sessions/{id}/checkpoints`
返回一份列表，事件流里也有每条 `CheckpointCreated`。两边的分页、排序、归属时刻都可以
各自演化，而界面只能信一个。

## 定了什么

- **删掉 `GET /api/sessions/{id}/checkpoints`**（以及 `SessionService.checkpoints`）。
- 回滚面板直接用 SSE 折出来的那份 `items`：`CHECKPOINT_CREATED` 折成不显示的
  `checkpoint` 条目，`fold` 给它盖上信封的 `seq`；面板按 `turn` 去重、按 `seq` 定位。
- **SSE 连上时会补历史**，所以打开一条老会话就有全部位置，不需要第二次请求。
- 按提交合并（`toCommitSha`）需要的 sha 也从同一条事件的 payload 里取 —— 测试和界面
  现在读的是同一份。

## 还考虑过什么，为什么没选

- **保留接口，把它做对**：那仍然是"同一份事实两个来源"。界面的需求（整条会话的位置、
  和屏幕上那段对话由同一份 fold 得出）已经由事件流满足；再维护一个 REST 投影，
  只能换来"两处迟早不一致"。
- **只给接口加分页参数**：从前界面用的就是它，坑已经踩过 —— 默认两百条，面板只看得到
  **最早**的两百条事件，最近的位置列不出来，而被回滚退掉的老分支位置反而还在。
- **让 `/events` 继续承担"拉历史"**：SSE 已经补历史；`/events` 留作一次性快照/导出，
  不作为回滚面板的依赖。

## 代价与换来的

- 只走 REST 的调用方要自己从 `/events` 里筛 `CHECKPOINT_CREATED`；目前没有这样的调用方。
- 换来的是：位置列表和屏幕上那段对话**同出一份 fold**，不可能对不上；删掉一个
  没有消费者的接口，和它背后那条会分页截断的路。
