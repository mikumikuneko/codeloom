# 决策：模型能力表砍到只剩真正会变的那几个

## 是什么问题

模型能力表（`ModelCapabilities`）一开始按我们用的那一家模型的形状设计了一堆字段。问题是：其中大多数没有读者，而且它们的形状是**一家 provider 的私有形状**。

## 定了什么

砍到只剩真正会变、而且真有人读的：`supportsTools` 和 `contextWindow` —— 后者也不是它自己的字段，而是**压缩功能真的需要**它。

## 还考虑过什么，为什么没选

- **保留整套字段**（"以后接别家会用到"）：没有读者的字段比没有它更糟 —— 它会让后来的人以为"系统在这一层上区分这些东西"，于是照着它写代码。这条和"不把单一 provider 的设计当成通用设计"是同一条纪律。
- **把所有模型差异都收进这张表**：表一旦开始承载"别家的形状"，就会变成一张要跟着上游 API 走的清单 —— 那是适配层的事，不是领域层的事。
- **一个字段都不留**（连 `supportsTools` 也删）：它真有读者（决定要不要把工具定义发过去），删了就要在调用处硬编码。

## 代价与换来的

- 走过一次"删了又加回"：`contextWindow` 在清理死代码那轮被删掉，同一周因为压缩需要那个数又加了回来 —— 教训是**删字段之前先把"谁会读它"问一遍**，别只看"现在有没有人读"。
- 换来的是：领域层里没有一家 provider 的私有形状；适配层承担差异，领域层只保留"我们真的要用到的区别"。
- 又走了一次回头路：单次输出上限（`maxOutputTokens`）当初因为"没人读"被删，后来**需要它了，又加回来**（"等真有代码要读它的时候再加"—— 那个时刻到了）。两次都不是错，但它们合起来说明一件事：删字段之前要把"谁会读它"问一遍，而不只是看"现在有没有人读"。
