# 决策：只有一个实现的"接口"，降级成类

## 是什么问题

`CommandPolicy` 是一个接口（还带 `@FunctionalInterface`）。但全项目只有一个实现、一个调用点。

## 定了什么

**降级成 `final class`**（不删，因为它的职责是真实的：判断"这条命令要不要问人"）。

## 还考虑过什么，为什么没选

- **原样留着接口**：一个实现、一个调用点 —— 这个"接口"没有在提供任何选择，它只是让读代码的人以为"这里可以换别的策略"。而那种错觉会让人为它写不必要的抽象（第二、第三个实现）。
- **整个删掉、调用方直接传一个 `Set<String>`**：那会把"带路径的命令一律要问"这条判断从它该在的地方（策略）挪到调用方（散在 set 的构造处），是变差。
- **等真出现第二个实现再说**：那正是不做接口的理由 —— 出现第二个的时候再抽，成本比现在猜一个便宜。

## 代价与换来的

- 将来真需要替换策略时，要花一次"把类抽成接口"的功夫（很便宜，而且那时才知道接口该长什么样）。
- 换来的是：**页面上没有一条假的扩展点**；这次改动只动这一个文件，调用方一行都不用改，行为零变化。
