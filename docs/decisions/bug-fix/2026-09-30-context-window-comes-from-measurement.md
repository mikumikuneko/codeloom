# 决策：窗口不写死，用量以真实读数为锚

## 是什么问题

"什么时候该压缩历史"依赖两个数：窗口有多大、现在用了多少。两个数最初都是猜的（写死 64k、每次都从头按字符数估），于是"用了 82%"这种显示是错的，压缩的时机也是错的。

## 定了什么

- **窗口**由模型能力表给（现在用的这家是 1M），不写死在代码里；**认不出模型时退回 64k**。
- **用量先取真实读数**（provider 每次回复带的 usage），只有"最后一次读数之后新增的那些消息"才用字符数估算增量。
- **压缩的触发**：阈值照旧，但撑到临界时用 `ContextCompactor.Trigger.OVERFLOW` 那条路 —— 不看估算，因为估算器可能刚好错过一次。
- 压缩要留的余量按窗口比例封顶（四分之一）。

## 还考虑过什么，为什么没选

- **写死 64k**（原来的做法）：实测把它推翻了 —— 把 30 万 token 的请求发过去，对方正常回答案；把验证码放在最开头，它一字不差地回了回来。原来那个数是错的，"82%"是分母错了。
- **所有模型一律按 1M 算**：对别家会高估窗口，于是压缩永远不触发，最后撞在对方的上限上。
- **每次都从头全估**：中文会被系统性低估，而误差直接落在总数上。以真实读数为锚，只估增量，误差就不会累积。
- **拿不到窗口就报错**：本地跑的时候会直接起不来 —— 退回一个保守值更合适。
- **不留余量 / 余量写死**：写死的那个余量是按 1M 定的，照搬到 64k 的窗口上会算出负数，所以按窗口比例封顶。

## 代价与换来的

- 依赖 provider 真的回 usage；不回就只能退回估算。
- 那个"四分之一"的系数是**我们自己定的，没有外部依据** —— 这一点如实记着，它是个参数而不是结论。
- **动因**（这条决定了整个上下文的策略）：prompt 缓存的命中价是未命中价的**五十分之一**。所以"只往尾部追加、不重写前缀"是一条有价钱的纪律，压缩是它唯一的例外 —— 也因此压缩必须**罕见**。附带一条：前缀里不能放每次都变的东西（比如时间戳），否则每轮全未命中。
- **溢出的恢复是单独一条路**：阈值估算错了怎么办？provider 明确回报"上下文超了"时走 `Trigger.OVERFLOW`（**不看阈值**，因为估算器可能刚好错过一次），循环里注入一次修复、**最多修一次**（修不动就如实失败，不无限重试）。别处也都有这层兜底，而"阈值算错"是常态 —— 我们自己的窗口常量就错过 15 倍。
- 换来的是：界面上的用量是真的，压缩在"真的快满了"的时候发生，而不是在一个错的分母上。

## 什么情况下该重新考虑

接第二家 provider 的时候：窗口大小、usage 的语义、以及"不回 usage 的 provider 怎么估"都要重新核一遍。
