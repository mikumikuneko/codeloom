# 决策：正在等人批的调用，别告诉模型它"中断了"

## 是什么问题

一条工具调用请求了、却还没有结果时，投影要给模型补一条 tool 消息 —— 这不是好看不好看的问题：**API 要求每条 `tool_calls` 都配一条 tool 消息**，不配下一次请求直接 400。所以 `MessageFold.closeOpenCalls` 是发给模型之前的最后一道兜底，它补的那句一直是：

> （这次调用没有留下结果 —— 那一轮在它执行期间中断了。不要直接重试，先确认相关文件的当前状态。）

而**正在等人批**的那条调用也落在同一支里：它请求了、没有结果 ✓，于是模型被告知它"执行期间中断了"。它其实**压根没跑过** —— 它在等一个人点批准。那句"不要直接重试，先确认相关文件的当前状态"因此是反的：那条命令还没执行，没有"当前状态"要确认。

**这不是一句写了白写的错话**：挂起期间投影确实会被送出去一次 —— 一轮恢复时会先跑压缩，而压缩器把这份历史喂给摘要模型，摘要一落下去就顶替整段历史。（补跑那条批准的调用发生在**进模型循环之前**，所以真正给主模型看的那份已经是对的了；错的那份只在压缩那条路上被读到。）

## 定了什么

`MessageFold` 记住哪些调用**已经问了、还没答复**（`awaitingApproval`），兜底时分开说：

- 等人批的 → 「（这次调用还在等你批准，没有结果。）」
- 真的中断了的 → 原来那句不动。

答复一到就把它从那个集合里摘掉；回滚截断时也按"请求还在不在"一并清掉（和它旁边那两个集合同一条规则）。

## 还考虑过什么，为什么没选

- **挂起时干脆不补这条合成消息**：那正是 400 要回来的样子 —— 投影里会出现一条**没有人回应**的 `tool_calls`，而这条兜底存在的全部理由就是防它（挂起期间同一条路要过压缩器）。
- **把这条调用从"待收尾"名单里摘掉**（前端就是这么做的：那条规则是"批过的调用不能扫"）：前端可以这么做，因为它的兜底只在**一轮真的收尾**时跑；这里的兜底是**每次折完都跑**的，挂起那一刻正需要它来配那条对。
- **不管它**（只在注释里记一句"这句话到不了模型"）：不成立 —— 压缩那条路是活的，而且"到不了模型"依赖的是别处的一个不变量（补跑必须排在模型循环之前）。

## 代价与换来的

- 代价：`MessageFold` 多一个集合，和它旁边那个"待收尾"的集合要一起维护（截断、答复时各清一次）。
- 换来：投影里不再有一句关于这条时间线的假话。模型（以及摘要）看到的"这次调用怎么了"，几种处境各自是真的。

## 顺带把「哪些事件算一次调用的终局」收成一处

查这件事时发现：问"哪条事件把这次调用推到了哪一步"的地方**有两处各列了一遍**（投影那边是 `instanceof` 链、崩溃恢复那边是带 `default` 的 switch），而**漏掉一种终局事件不会报错** —— 恢复会给一条早就结束的调用再补一条"进程重启、没有完成"。

现在收进 `ToolCallLifecycle`：它只回答"是哪一步"（请求了 / 有结局了 / 挂起等人批 / 批了 / 拒了），**不回答"那一步意味着什么"** —— 同一件事对不同的人含义相反，这是刻意的：`ToolApprovalRequested` 在投影那边算"还没收尾"（那条 `tool_calls` 还等着配对），在崩溃恢复那边算"不是执行到一半"（那条命令压根还没跑）。两处于是都变成"拿步名做自己的事"，读起来就是各自规则那句话。

- **终局是那四种**：跑完、被取消、被中断、被拒绝。`ToolRejected` 从前在崩溃恢复那边是个空分支（靠"挂起时已经摘掉了"侥幸成立），现在它**在定义里**就是终局。
- 实现是**一个穷尽 switch 表达式，不带 `default`**。实测过两次：删掉一个空分支 → 「switch 表达式不包含所有可能的输入值」；把"被拒绝"挪出终局 → 分类测试当场红。
- `ContextCompactor` 那处**没动** —— 它的 `default` 注释写着理由是"它是**筛选**而不是映射"：漏掉一种事件只是"不选它"，而它本来也不在名单上。
