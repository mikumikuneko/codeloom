# 决策：被拒绝的调用补一条自己的终局事件

## 是什么问题

用户拒绝一次工具调用之后，事件流里留什么？什么都不留的话，那条调用会永远停在"正在跑"的样子（界面上 outcome 为空就等于在跑），而且模型下一轮看到的是一个没有结果、也没有结局的调用。

## 定了什么

新增一个独立事件 `ToolRejected`：拒绝在事件流里就是一条**终局记录**。**不复用** `ToolResult(success=false)`，也**不只改前端**。

## 还考虑过什么，为什么没选

- **复用 `ToolResult(success=false)`**：那违反我们自己已经写在 `ToolCancelled` 注释里的规则 —— "记录成独立事件，而不是把结果标成失败，因为那是用户意图"。后果也很具体：崩溃重放之后，模型会理直气壮地**重试用户刚刚拒绝掉的操作**；审计上也分不清"这次调用挂了"和"用户不想跑"。
- **只改前端**（界面上把那条标成"已拒绝"）：事件流里根本没有这个事实，刷新一下就没了 —— 那是把事实层的问题当成显示层的问题。
- **让审批的答复事件顺带充当结果**：审批答复是"谁批的、批的是什么"，它和"这次调用最终没发生"是两件事；而且"批准"那条路本来就要往下跑，把两种结局塞进一个事件会让消费者分叉。

## 代价与换来的

- 动的地方多：sealed 层级、编解码、投影、前端各一处，加相应测试。
- 换来的是："拒绝"和"失败"在**事实层**就分得开 —— 崩溃重放、审计、模型上下文读到的都是同一件事。
- **一个孪生 bug 一起记着**：那条路当时**只落库、没广播**（`abortTurn` 的返回值被丢掉了）—— 于是库里对、屏幕上不对，而且不报错。同一件事的两个面："落下了"和"推出去"必须都做。
- 前端另加一道兜底：收尾时把**一直没有结局的调用**标成"没有结果"（而不是让它一直显示成"正在跑"）。
