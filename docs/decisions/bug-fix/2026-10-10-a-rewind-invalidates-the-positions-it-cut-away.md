# 决策：回滚要把自己记的"消息里的位置"一起作废

## 是什么问题

投影把事件流折成消息时，顺便记了几张**按消息下标索引**的表：每条工具调用的结果消息落在哪一格、每条 checkpoint 对应哪一格、哪些调用还没结局。

回滚是唯一一处**回头砍已经投出去的消息**的地方。它只砍了消息数组的尾巴，那几张表**一个字没动**。于是回滚过一次之后，它们记的下标指的是**已经被砍掉的位置**，或者更糟 —— 指的是别人。

三种症状，都实测了：

- `toolMessageAt`：同一个调用 id 再被答复时"原地替换"，**下标越界直接抛出去**（实测崩在 `answerCall`）；下标要是还在范围内，就是**静默覆盖一条无关的消息**。
- `openCallIds`：收尾会给"请求了却没有结局"的调用补一条结果 —— 而它的请求已经被回滚砍掉了。补出来的是**一条前面没有 `tool_calls` 的 tool 消息**，下一次发给模型直接 400（实测到）。
- `checkpointIndexes`：再回滚一次会按旧下标截，截错地方。

前两条都实测到了；`checkpointIndexes` 那一条是同一个根因的第三种表现，修法是同一行。

## 定了什么

`truncateTo` 砍完消息之后，把界外的位置一起扔掉：

- `toolMessageAt` / `checkpointIndexes`：删掉下标 `>= from` 的条目。
- `openCallIds`：删掉那些**请求已经不在剩下的消息里**的调用 —— 判据是回到 `messages` 里去找那条带 `tool_calls` 的 assistant 消息，而不是另记一张表（"这次调用落在哪一格"已经从消息本身读得出来）。

## 还考虑过什么，为什么没选

- **只在 `answerCall` 里加一道下标越界的检查**：它只能挡住"崩"，挡不住"下标还在范围内、于是**静默覆盖别人的内容**"；而孤儿 tool 消息那条路根本不经过它。
- **给每个调用另记一张"请求落在哪一格"的表**：多一张要跟着消息一起维护的表，而那份信息 `messages` 里本来就有 —— 多一份就多一个走样的地方。

## 代价与换来的

- 代价：`openCallIds` 那一条要扫一遍切点之前的消息。回滚很少发生，这一次扫描不值一提。
- 换来：回滚之后投影的记账和消息**对得上**了 —— 崩、静默覆盖、下次请求 400 三条路一起堵上。
- 一条前提写在这里，省得将来有人踩：`checkpointIndexes` 是在**整条流**上预扫描出来的（见 `begin`），所以它跟"消息一条条长出来"这件事绑定；回滚一旦让两者错开，就必须由这里收拾。哪天换成增量维护，这条要跟着重新想。
