# 决策：冲突没收尾时，再点同步或合并是 409，不是 500

## 是什么问题

一次合并撞出冲突之后，会话的工作区里留下了一个未完成的合并（`MERGE_HEAD` 还在）。
此时顶栏的「同步」和「合并」**仍然可以点**，而 git 不允许同一块工作区里起第二个
未完成的合并：命令以非零退出，抛成 `GitCommandException`，没有翻译，客户端看到的是

```
请求失败（HTTP 500）
```

一句和真实原因无关的话。真实的下一步只有两个：裁决冲突，或者放弃合并。

## 定了什么

- `SessionSyncService` 在同步之前、`ProjectMerger` 在合并之前，先看
  `mergeInProgress`（树的工作区和主干两处都看）。有未收尾的合并就抛
  `ResponseStatusException(CONFLICT, "…还没收尾：先在中间裁决冲突，或者放弃合并")`。
- 前端在 `conflicts` 清单非空时禁用「同步」「合并」两个按钮，并在 `title` 里说原因。
- 后端仍然会拒 —— 按钮禁用只覆盖"用户看得见的那条路"，不能替代服务端的判断。
- 冲突裁决页的标题按**用户刚点的按钮**说：点合并撞出的冲突写「合并时撞上的」，
  而不是按方向写「同步时撞上的」（合并内部会先同步，方向也是 `INTO_SESSION`）。
  刷新之后分不出点击来源，退回按方向说。

## 还考虑过什么，为什么没选

**把 `GitCommandException` 统一映射成 409。** 那会把真正的 git 故障（磁盘满、仓库损坏、
超时）也说成"你还有一步没做"，而用户会照着这句去裁决一个不存在的冲突。要映射就得
按错误文本判断，那又是一份会随 git 版本变化的字符串匹配。

**冲突没收尾时自动 abort 再合并。** 放弃哪一侧的改动是一个**人的决定**，不能由一次
点击顺带做掉；而且"自动 abort"会把用户刚编辑到一半的冲突文件内容抹掉。

**只在界面上禁用按钮。** 后端仍可能被直接调用（脚本、旧页面、并发窗口），
而那个 500 恰恰是从服务端来的；只拦客户端等于把同一件事修一半。

## 代价与换来的

- 每次同步/合并多几次 `git rev-parse`（读 `MERGE_HEAD`）：同步看树，合并看树和主干。
  可忽略。
- 409 现在多了一种文案。客户端的 `act` 已经按"有没有 `conflictingPaths` /
  `commitsBehind`"分流，这一种落到 `else` 里把 detail 原样显示 —— 不需要再加分支。
- 换来的是：用户不会再从一个"服务器坏了"的假象里猜下一步，而是被直接告知
  "先裁决，或者放弃"。
