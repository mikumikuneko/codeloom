# 决策：轮次号按"这一轮跑完了吗"推进

## 是什么问题

会话行上有个"第几轮"的数，界面用它定位、模型上下文用它截断。那么：挂着等人批的时候，这个数推不推？批准之后接着跑完，推不推？失败、被打断算不算一轮？

最初这条规则的注释写着"两者都算轮次结束，轮次号照样推进" —— 那句话本身就是被推翻的那个设计。

## 定了什么

判据是**"这一轮跑完了吗"**（`completes(finalState)`：终态不是"等人批"就算跑完）。挂在审批上不算跑完 —— 号等到批准、续跑结束之后才推。失败、取消、拒绝也算一次交互结束，号照样推。

同时把 checkpoint 的写入挪到推进**之后**，让两处写的是同一个值。

## 还考虑过什么，为什么没选

- **让界面不依赖这个字段、自己数用户消息**：那只是让界面不受影响，字段自己"一次写一个值、下次写另一个值"的矛盾还在。
- **批准/失败/中断一律推进**（原来的写法）：挂着等人批时它并没有跑完，号推了之后界面会把"还没结束的这轮"当成上一轮。
- **批准续跑也推一格**：那会让界面上的轮次从第一次批准开始**全部错位一格**，而且是"看着差不多、其实全错"的那种错法。
- **用一个独立的"用户消息序号"当界面键**：界面上确实另有一处这么做了（"这一轮改了什么"按第几条用户消息分组），但那是为了绕开"批准会让后端号多推一格"；这里要修的是字段本身。

## 代价与换来的

- 改了写入顺序（checkpoint 落在推进之后），旧数据没有回填（开发阶段）。
- 换来的是：这个数只有一个写值，"跑完了没"这一件事在代码里只有一处判据，界面、上下文、审计用的是同一个数。
