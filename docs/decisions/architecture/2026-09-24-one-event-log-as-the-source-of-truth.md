# 决策：只建一张事件表，它是唯一事实来源

## 是什么问题

两个人的 agent 在同一个仓库上干活。每一轮的对话、工具调用、审批、检查点都存在哪儿？换个说法：一轮跑完之后，凭什么能回放它、断线之后凭什么能补齐、出了问题凭什么能倒回去？

## 定了什么

只有一张 `event` 表，append-only —— `EventStore` 的类注释第一句就是"永不修改、永不删除"。主键是全局自增的 `BIGINT`，它就是 `seq`：不是"会话内的第几条"，跨会话也单调。追加事件要求一个 `LeaseToken`，这是 fencing 的落点，没有 token 就走不了 `append`。

模型看到的一切都是**投影**出来的：`ContextAssembler` 每轮从事件流装配模型请求，不另存一份消息数组。事件类型名是持久化格式的一部分 —— 改一个常量名，历史行就整体读不出来，所以 `EventTypes.parse` 遇到读不懂的类型**直接抛**，不安静跳过。唯一的删除是丢会话时的 `EventDiscard`，它自己带一整套理由。

## 还考虑过什么，为什么没选

- **消息表 + 工具调用表**（传统关系表）：单看查询是简单的，但要把一条对话拼起来还是得按序号拉全量再聚合，而且回放、回滚、断线补齐会各写一套。改成单表事件之后，这三件事和审计、崩溃恢复共用同一套机制 —— 查询麻烦这一点是主动付掉的。
- **可变的消息数组，事件只当通知**：状态和日志会分叉。事件溯源里日志就是状态，所以分叉在结构上不可能发生 —— 这是选它的全部理由，也是不选数组的全部理由。
- **用的时候现问 git / 现算**（"这一轮改了什么"曾经是每次请求重算一次）：这等于让 git 变成**第二个事实来源**，而 git 里的东西会变（对象被 gc、树被回收、分支被 reset），历史记录不该依赖"以后还能算得出来"。后来改成写时算一次、落成 `WorkspaceChanges` 事件。
- **落一张快照表做跨轮缓存**：要加表、加迁移，而"没有迁移机制"正是这个项目最弱的一环；而且真正的开销在反序列化与重放（CPU），不在那次 SQL。

## 代价与换来的

- 读一条会话的完整对话要按 `seq` 拉全量再聚合，比"一张消息表"麻烦。
- 投影的派生成本随日志长度线性增长；缓解手段是压缩（`ContextCompacted`），**不是**回头改日志。
- 写时算的记录**不能重算**：以后改了算法（比如路径映射修了 bug），历史记录不会跟着变对。
- 换来的是回放、回滚、断线补齐、审计、崩溃恢复这五件事共用一套机制，而且"模型看到的东西都能从日志重建"成了一条结构性的保证，不靠自觉。
- 那条保证有一对：**模型可见的，必须落库**；反过来，**日志里读不懂的东西，拒绝整条日志，不跳过** —— 跳过等于让投影安静地少一条事实，而投影就是模型的上下文。
- 还有一条取舍要写下来：**"这一轮改了什么"是写时算一次、落成事件，不是在读的时候问 git**。读时算看着更省，但它让 git 变成第二个事实来源 —— 而 git 里的东西会变（对象被 gc、树被回收、分支被 reset）。代价是"记录不能重算"：以后算法修了 bug，历史记录不会跟着变对。
- **已知的缺口**：事件 payload 没有版本化机制。改一个字段的含义，历史行不会跟着变 —— 这是目前最弱的一环，写在待办里。

## 什么情况下该重新考虑

单条会话长到"装配一次投影"成为瓶颈的时候（现在是每轮装配若干次、随日志增长）。那时该动的是缓存与淘汰，不是这张表。
