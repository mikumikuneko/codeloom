# 决策：Redis 的淘汰策略是 `noeviction` —— 这是一条正确性配置

## 是什么问题

Redis 的 `maxmemory-policy` 怎么写？默认答案（"Redis 就是个缓存"）是 `allkeys-lru`：内存满了就淘汰最久没用的键。

## 定了什么

**`noeviction`** —— 写满就报错，一个键都不淘汰。

## 还考虑过什么，为什么没选

- **`allkeys-lru`（或任何会淘汰的策略）**：问题不在于"缓存会丢"，而在于**执行租约住在 Redis 里**。一把租约被淘汰，等于锁凭空消失 —— 两个人可以在同一棵树上同时跑，而他们各自的写入都会通过自己的 fencing token（因为推号的过程没有感知到锁没了）。这类 bug 的症状是"偶尔有一次工作区被踩"，几乎不可能复现。
- **把租约挪出 Redis**：那要放弃 `SET NX PX` 的原子性和到期自动释放，换成一把要人管的锁 —— 得不偿失。
- **不设上限**（让 Redis 自己长到 OOM）：那是最坏的一种，表现为"某一刻整个服务崩掉"。

## 代价与换来的

- 内存写满会让写入直接失败（这是要的），所以容量要有人盯着 —— 这条从"性能问题"变成了"运维事项"。
- 换来的是：**"锁不会凭空消失"由配置保证**，而不是靠"内存够用"这个随时会变的假设。与之配套的那条是"fencing 的发号放 MySQL"——**锁可以在 Redis，计数器不行**。
