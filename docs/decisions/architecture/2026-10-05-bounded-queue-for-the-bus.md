# 决策：事件总线的线程池换成有界队列 + 调用者执行

## 是什么问题

往浏览器推事件的那条线，背后是一个线程池。用 `Executors.newSingleThreadExecutor()` 是最省事的写法 —— 但它的任务队列是**无界**的。

## 定了什么

显式的 `ThreadPoolExecutor`：**有界队列**（容量一万）+ **`CallerRunsPolicy`**（队列满时由提交者自己跑）。

## 还考虑过什么，为什么没选

- **保持原样、加一句注释说明"队列是无界的"**：注释不解决"内存会悄悄涨到 OOM"这件事，而那种崩法是"跑了几小时之后突然死"，最难查。显式队列让这个上限在代码里看得见。
- **换成 Spring 的 `ThreadPoolTaskExecutor`**：多一层包装，而我们要的只是"有界 + 一个明确的拒绝策略"。
- **有界 + 丢弃最老的**：事件是事实，丢一条比慢一点严重得多。

## 代价与换来的

- **队列真满时，`CallerRunsPolicy` 会短暂堵住提交者** —— 而提交者可能是 Redis 的 I/O 线程，那正是当初拒绝"在 I/O 线程上跑业务"的理由。所以这条取舍要写在明处：**我们选了"宁可慢，不丢帧"**；如果你更在意"I/O 线程绝不被堵"，那就该换别的拒绝策略（丢最老、或者丢当前）。
- 队列容量"一万"是**猜的数**，注释里如实标了。它该做的不是调大，而是等有真实压力数据时重定。
- 换来的是：内存占用有一个写在代码里的上界，而不是一个默认的无界队列。
