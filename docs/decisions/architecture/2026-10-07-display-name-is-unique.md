# 决策：用户名唯一

## 是什么问题

显示用的用户名（`display_name`）要不要唯一？原来是不唯一的（注释里也写着"不唯一"）。

## 定了什么

**加唯一约束**。连带一处必须改的地方：保存用户的 mapper 从 `ON DUPLICATE KEY UPDATE` 改成"先更新、没有再插入"。

## 还考虑过什么，为什么没选

- **保持不唯一**：那"事后查得出是谁"这件事兑现不了 —— 事件里存的是 id（对），但人要读的时候按名字读，两个同名的账号会让追溯变成猜。而且用户提的理由很直接：大部分平台都要求用户名唯一。
- **只在应用层查重**（不加数据库约束）：并发注册能穿过去，而"重名"这件事一旦发生就再也回不去。

## 代价与换来的

- 那句 mapper 的写法必须一起改：表上现在有**两个唯一键**（账号、显示名），`ON DUPLICATE KEY UPDATE` 会在撞到第二个键时**改掉另一个用户的行** —— 一个只在重名时才出现的、非常难复现的数据损坏。这类"加了唯一约束就要重新看一遍写入"的连带，是加约束的真实成本。
- 换来的是：名字可以当"人读的标识"用，而追责仍然走 id。
