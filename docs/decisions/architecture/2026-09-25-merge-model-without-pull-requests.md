# 决策：合并没有 pull request 那套 —— 主干只读、合并不自动、不需要批准

## 是什么问题

两个人的改动怎么交汇？要不要走上"提 PR → 审查 → 批准 → 合并"那条常见路径？

## 定了什么

- **必须有一棵主干**（`main`），**主干只读**：谁都不在自己树里直接改它，改它只有"合并"这一条路。
- **合并是人点的动作**，不自动发生；**不需要对方批准**。
- 合并另用一把 **MySQL 的项目行锁**（不是复用会话租约，也不是第二把 Redis 锁）——这把锁要跨多个 HTTP 请求（从发现冲突到裁决完成）。
- 合并落地之后**自动在主干上跑一次验证**。

## 还考虑过什么，为什么没选

- **PR 那套（分支 + 审查 + 批准）**：它的前提是"两个人看不见彼此的工作、要靠审查兜底"。而我们的前提正相反 —— 两个人实时看着同一场会话。那套流程的价值会被核心功能取代，留下的只有仪式。
- **不要主干、两端直接互合**：那样合并不传递（A 和 B 各合各的，第三次就成一团乱麻），而且"此刻正确的版本"没有一个落点。
- **自动合并**：git 能把改动合并到一起，不代表语义是对的（两边都改了一个函数的契约，git 会安静地通过）。判断该由人做。
- **复用会话租约当合并锁**：执行租约只护一条会话，而合并改的是所有人共享的主干 —— 粒度不对。
- **不做合并后的验证**：合并是**唯一一条"代码变了却没有验证兜底"的路径**（agent 每轮跑完都有验证，合并没有）。不补这一刀，主干上就可能躺着编译不过的代码。

## 代价与换来的

- 合并是个显式动作（要有人记得点）；主干上的验证会占一点时间。
- 换来的是：**"主干上永远是能跑的代码"是结构性的**，不是纪律；而"谁的改动进来了、什么时候进来的"在主干的历史里看得见。
