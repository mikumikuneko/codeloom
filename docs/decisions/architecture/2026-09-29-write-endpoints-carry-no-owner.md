# 决策：写接口一律不带 owner，只有读接口能指定"看谁的那棵树"

## 是什么问题

工作区是"每个人一棵树"。那么操作工作区的接口（列文件、读文件、写文件）要不要带一个"对谁的那棵树操作"的参数？—— 观战需要看**对方**的代码，读接口不给这个参数就不够用。

## 定了什么

**读接口可以有 owner（可选，默认自己），写接口一个都没有**。写就是写**自己的**树，这个前提写死在权限检查里，不是靠传参。

## 还考虑过什么，为什么没选

- **写接口也带 owner**（跟读接口对称）：那等于"我可以删掉对方工作区里的文件"。而那棵树**是唯一一处只有他自己能改的地方** —— 它存在的意义就是"这是我的地盘"。对称在这里是错的方向。
- **只在文档里说明"owner 要传自己"**：那是把安全边界交给调用方的自觉。
- **干脆取消 owner 参数**（连读也不给）：观战就看不到对方的代码，而"看得见"是这个产品的核心。

## 代价与换来的

- 读和写的参数形状不对称（读多一个可选参数），读代码时要看清是哪一个。
- 专门钉了一条测试：往写请求里塞一个别人的 owner，断言文件**仍然落在自己的树里** —— 这条测试就是这条决策的执行者。
- 换来的是：安全边界由一个**接口形状**保证，而不是一句约定。
- 文件接口还有三条一起定下的细则：**按项目级而不是会话级**（文件是"树"的属性，而观战的时候人还没进任何会话）；**隐藏名单只有 `.git` 和平台的目录**，刻意不去猜 `target`、`node_modules` 这类（猜错一次就让人以为文件丢了）；**路径守卫复用 agent 那一份**，不另写一套 —— 两套守卫迟早走岔，而走岔的那一套就是漏洞。
