# 决策：回滚退整棵树，坐标是事件序号

## 是什么问题

用户点"回到第 3 句之前"的时候，退的到底是什么？是这条会话动过的那些文件，还是这棵树上的全部改动？以及：拿什么去指认"那个时刻"？

## 定了什么

**退整棵树**：`SessionService.rewind` 先抢租约，再 `WorkspaceManager.resetTo`（`reset --hard` 加上 `GitClient.cleanUntracked` —— 后者不能省，`reset --hard` 不碰未跟踪文件，而 agent 刚写出来、还没进任何 checkpoint 的恰恰是未跟踪的），然后对话截断、落 `SessionRewound` 留痕。一棵树属于一个人，所以"撤销"就是整块撤销。

**坐标只有事件序号**：`SessionCheckpoints.requireAt(session, seq)`，回滚事件里记的也是 `toCheckpointSeq`。commit sha 仍然留着 —— 但只作为"回滚之后的 git 位置"，审计和 diff 记账用，**不再承担定位职责**。

## 还考虑过什么，为什么没选

- **只退这条会话动过的文件**（实现过一版：`SessionTouchedFiles` + `restorePaths`，HEAD 不动）：退的边界应该是"我这棵树"，同步带进来的东西既然已经在我的分支上，不退就说不通。当时的错在于把"回滚单位"也照着别人的做法抄了 —— 别人按文件圈范围是因为它的目录上所有会话共用一份文件、没有分支可用，我们有分支，所以那个单位对我们没有理由。
- **用 commit sha 当坐标**：一轮什么都没改时，两条 checkpoint 会同 sha。这个 bug 的具体样子记下来：同一个 sha 在一条会话里出现了 **5 次**，"取最早匹配"取到的是**会话创建那一刻**，于是"回到第 3 句之前"变成整段对话被清空。而且当时**三处各自**按 sha 找"第一条"（后端定位树、模型上下文截断、前端屏幕截断）—— 同一个错在三个地方各写了一遍。
- **按 `turnIndex` 截断对话**：会话起点和第 0 轮的 turnIndex 都是 0，会撞。改成按 checkpoint 的 sha 精确截断，并且用 `putIfAbsent` 与"取第一条"的语义对齐；兜底是清空。
- **`{sha, turnIndex}` 两条一起比**：回滚过一次之后，被退掉那条分支的 checkpoint 还在库里，`turnIndex` 撞上时"最早匹配"会命中旧分支那条 —— 不稳定。
- **每轮加 `--allow-empty` 让 sha 唯一**：历史上会多出一串什么都没改的提交，跟着同步和合并一起走。
- **回滚前检查"目标之后有没有别人的提交"，有就 409**：已删除。它守的是一个不存在的伤害 —— 那些提交在主干里、在别人自己的树里一点没少，我下次同步就拿回来了；代价却是同步过一次之后再也回不到同步前。

顺带删掉了回滚事件里只写不读的 `toTurnIndex` / `fromTurnIndex`：留一个没人读的轮次字段，等于给下一个读代码的人一个"轮次也是权威坐标"的错觉。删掉之后，整个项目只剩**一个**定位概念 —— seq。（轮次本身没丢，会话行上那个数照旧。）

## 代价与换来的

- 人手建在工作区里的文件**活不过一次回滚**（`clean -fd` 连未跟踪的一起删）。这是"撤销就是整块撤销"的代价，写在了 `manual-file-ops` 那条约定里。
- 回滚之后回不到"同步前"那个状态（曾经那条 409 检查想守的东西，其实守不住也不该守）。
- 换来的是：定位只有一个概念，不可能撞车；回滚的语义能用一句话说清 ——「我这棵树回到那一刻」。
