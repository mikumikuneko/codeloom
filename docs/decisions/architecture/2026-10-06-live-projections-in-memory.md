# 决策：跨轮的投影放内存，数据库仍然是唯一真相

## 是什么问题

一轮里要装配好几次上下文（每次模型调用前）。每次都从第 0 条事件折一遍，成本随会话长度线性增长 —— 而且一条长会话每轮要折二三十次。要不要缓存折到一半的结果？

## 定了什么

两级缓存，都在**进程内存**里：

- **轮内的"可推进投影"** —— 一轮之内反复用同一份，不再重折。
- **跨轮的"活投影"** —— 同一个会话跨轮保留（有上限），每次只从"上次折到哪"往后接。

数据库那边一条都不加：**内存里的东西丢了就重建**，重建的源头永远是事件流。

## 还考虑过什么，为什么没选

- **落一张物化快照表**：要加表、加迁移 —— 而"没有迁移机制"正是这个项目最弱的一环；而且真正的开销在反序列化和重放（CPU），不在那次 SQL。**用最弱的一环去换最便宜的那一半，划不来。**
- **每次从头折（不做任何缓存）**：一轮里折 25 次就是 O(n)×25；会话越长越难看。
- **照搬一套插件化的投影注册表**：那需要"至少两个实现"才回本（我们只有一个折叠单元），抽象本身比它解决的问题贵。

## 代价与换来的

- 缓存**必须有上限**（我们是服务端、多会话、还打算能多实例）—— 而**淘汰路径当时没做**（那份表只增不减）。这是明确记下来的缺口：压测压不出它，因为假模型的对话太短；真实用户聊到几百轮时才会显形。
- 换来的是：装配成本与"新增了多少事件"成正比，而不是与会话总长度成正比；而且缓存是可丢弃的（它不承担任何事实责任）。
