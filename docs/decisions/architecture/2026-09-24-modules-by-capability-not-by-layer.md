# 决策：按能力切模块，不建 `common`

## 是什么问题

五个模块怎么分？那些"好几个人都要用"的东西放哪？

## 定了什么

按能力切：`domain`（零依赖的模型与端口）/ `workspace`（git 与命令执行）/ `agent`（模型循环与工具）/ `realtime`（事件持久化与推送）/ `app`（Web 层与用例编排）。**不建 `common`。**

两条配套的判据：**表按模块归属**（`project`/`session` 归 workspace，`event`/`chat_message` 归 realtime，认证归 app）；**同一条规则的两半必须住同一个模块**。

## 还考虑过什么，为什么没选

- **一个 `common` 装"大家都用的东西"**：那是"不知道放哪"的默认答案。它会长成依赖图的中心节点、循环依赖的温床 —— 而且每次往里放东西都不需要做任何判断，这恰恰是问题。
- **按技术层切**（controller / service / repository 各一层）：改一个功能要横穿所有层，而每一层都必须知道所有能力。
- **给"编排"单独开一个模块**：app 的位置本来就是"唯一能同时看到四边的那个"，为它再开一层等于把同一件事说两遍（当年否掉 `common` 的理由同款）。

## 代价与换来的

- 有些东西看起来"两边都要"，得当场判断它属于谁。判据是"这条规则和谁的数据是一件事"：会话状态怎么迁移（`TurnStates`）因此从 app 搬进了 domain —— 它和 `SessionState.canTransitionTo` 是**同一条规则的两半**，分在两处没有东西强制一致，而不一致的表现是**跑到一半才抛**。
- 换来的是：依赖方向单向、单模块可纯单测、加一个能力只动一两个模块，而且"这个类该放哪"每次都有一个要回答的问题，而不是一个默认抽屉。
