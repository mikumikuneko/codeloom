# 决策：身份用 id，不用名字也不用地址

## 是什么问题

三处地方都要回答"这是谁/这是哪家"：密钥存在谁名下、会话连的是哪一家模型服务、事件里记的是谁。三处最初都用"看起来最直观"的东西当身份 —— 地址、用户名。三处都错了同一个方向。

## 定了什么

- **密钥按「账号 + 模型服务」存**（`(user_id, provider)`），不是一个账号一把。
- **会话记的是 `ProviderId`**（`ModelConfig` 里那一家的 id），不是 endpoint 地址。
- **领域事件里的人一律记 `UserId`**（`SessionRewound.byUserId`、`ToolApprovalResolved.resolvedByUserId`、`AgentNoteDelivered.fromUserId`），展示时按 id 现查用户名。

三处的判据是同一条：**唯一不等于它是身份。** 名字会改，地址是写法。

## 还考虑过什么，为什么没选

- **用地址当身份**（原来的做法，有一个 `EndpointHost`）：同一个服务可以有两个地址，两个地址也可能指向同一家；地址里差一个斜杠、大小写不同，就变成了另一家。所以那不是"少一层"，是换了个身份。
- **一个账号一把密钥**：用户配了 A 家再配 B 家会互相覆盖；更糟的一种是只配了 A 家却把会话切成 B 家 —— 那是**把 A 家的凭据发到 B 家的服务器上**，不是功能问题。
- **事件里记用户名**：追责要的是身份，而用户名会变。内部标识符不能当身份。
- **事件里 id 和当时的名字都记**：两个字段要保证一致，一旦不一致，"哪个是真的"没有答案；而且名字本来就能现查。

## 代价与换来的

- 同一个模型服务只能有一把密钥 —— 想用两个账号（一个测试一个生产）现在表达不了。
- 展示名字的每一处都要现查一次（换名字之后，历史事件上显示的就是新名字，这是有意的）。
- 旧数据：领域事件里的 `userId` 字段是后加的，之前的事件读出来是 null（开发阶段直接重建了库）。
- 换来的是：凭据不会送错服务器、审计能查到具体的人、地址怎么写都不影响"这是哪一家"。
- **和它并列、但方向相反的另一条规则**（别混）：**事件里存快照，不存引用** —— "谁捎来的"记当时的显示名，模型名记服务端实际回报的那个。判据不同：**追责要身份（记 id），展示要当时的样子（记快照）**；回放时用 id 现查名字会把历史改写掉，而模型名连"服务端到底用了哪个"都得靠快照才留得住。
- `ProviderId` 的构造只校验**形状**（小写开头的短串），"我们认不认识这一家"由"能不能取到地址"回答 —— 构造器不拦这件事。
