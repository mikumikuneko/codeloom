# 决策：加成员走邀请链接，不按用户名加

## 是什么问题

怎么把另一个人加进项目？直接按用户名/账号把他加进来，还是生成一条邀请让他自己接受？

## 定了什么

**邀请链接**：房主生成一个 token（随机 32 字节，不是 UUID），对方拿它访问 `/invite/<token>` 并接受（`InvitationService.accept`），这才成为成员。成员上限在**接受**那一步判（`Project.MAX_MEMBERS`）。

## 还考虑过什么，为什么没选

- **按用户名直接加**（同时删掉按用户名加的那个接口）：两条路做同一件事，迟早会在上限检查、留痕这些地方不一致 —— 一条记得判上限、另一条忘了，就是一个洞。
- **token 用 UUID**：UUID 里带着时间戳与版本信息，而且短、可枚举面更大；32 字节随机是这类一次性凭据更合适的强度。
- **由服务端拼好完整链接返回**：客户端本来就知道要拼成 `/invite/<token>`，服务端只给 token 就行 —— 少一处要把站点地址配进来的地方。

## 代价与换来的

- 加人变成两步（生成 + 接受），而且邀请是**一次性凭据**，得管它的有效期与用完作废。
- 换来的是：加人这件事只有一个入口（于是上限检查、留痕只有一处）；对方的加入是他自己确认过的动作。
- 三条细则定死了行为：**一个项目同时只有一张有效链接**（生成新的当场作废旧的 —— 两人项目一张就够，"并存"只会攒出一摞"已撤销"）；**自己点自己的链接早退、不烧凭据**（否则会作废本来要发给对方的那张，而界面上又看不出，于是人以为"对方已加入"）；**满员在被接受的那一刻判、不消耗链接**（状态不允许就不该毁凭据）。
