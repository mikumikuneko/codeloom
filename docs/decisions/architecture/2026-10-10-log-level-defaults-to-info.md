# 决策：日志默认 INFO，不默认开 DEBUG

## 是什么问题

`application.yml` 里原本写死 `com.codeloom: DEBUG`。那一档下 MyBatis 会把**每条 SQL 的绑定参数**打出来，而参数里有：

- 用户 API Key 的**密文**（`INSERT INTO user_api_key (… sealed_key …)`）；
- 口令哈希（`INSERT INTO user (… password_hash …)`）；
- 事件的 `payload` —— 也就是**整段会话正文**。

照抄这份配置去部署的人，日志里就有这些东西。而日志是最容易被复制、投递、留档的那份数据。

## 定了什么

`com.codeloom` 默认 `INFO`。要调试 SQL 时用环境变量临时开回来：

```
LOGGING_LEVEL_COM_CODELOOM=DEBUG
```

两个方向都实测过：默认那次 `Parameters:` 一行都没有，开了之后同一条测试里出现 107 行。

## 还考虑过什么，为什么没选

- **只压那几个 `*.persistence` 包**：看着更精准，但那是把"哪些包算敏感"变成一份要人维护的名单 —— 新加一个持久化包就会漏，而且漏了没人会发现。按包名列举和按变量名列举是同一种脆弱。
- **不动，只在文档里写"部署前压掉"**：默认不安全，靠读者自觉。仓库默认那份配置就是大多数人会照抄的那份，所以默认值本身就得是对的。
- **干脆把这一节删掉**（Spring Boot 的默认本来就是 INFO）：那样"能开 DEBUG"这件事就没有地方写了，而它恰恰是选这条路的代价所在 —— 代价要写下来，不然下一个人会以为我们只是忘了配。

## 代价与换来的

- **代价**：开发时默认看不到 SQL 了，要看得多敲一串环境变量；`log.debug` 写的那几行平时也不再出现。
- **换来**：默认那份配置拿出去部署，日志里不会自带密钥密文、口令哈希和会话正文。

## 什么情况下该重新考虑

如果哪天别的地方也把正文写进日志（比如给每个请求加了带 body 的 access log），要收的是那一处，而不是把这一档调回去。
