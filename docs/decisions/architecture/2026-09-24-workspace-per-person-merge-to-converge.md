# 决策：每人一棵 worktree，改动靠合并交汇

## 是什么问题

两个人的 agent 同时改同一个仓库，怎么不互相踩？同时又要让两个人能"实时看到对方在干什么"。这两件事一开始是被当成一件事设计的 —— 共享一份目录，谁改了什么彼此立刻可见。

## 定了什么

每人一棵 git worktree。树挂在「**人 × 项目**」上（`WorkspaceId(UserId ownerId, ProjectId projectId)`），分支名 `workspace/<ownerId>`，路径 `<root>/<ownerId>/<projectId>`。同一个人的两条会话**共用**同一棵树 —— 换一段对话不该让上一轮的改动消失，也不该多一个"隔离会话"开关。

两个人的改动**靠合并交汇**（`ProjectMerger` / `MergeService`），不靠实时同步。一棵树同时只有一把执行租约，所以同一个人的两条会话不能同时跑。

## 还考虑过什么，为什么没选

- **共享一份目录 + 文件级租约**：只防"同时写"，不防"先读后覆盖"；而且没有历史审计、没有回滚。
- **共享一份 + 写入要人 accept**：实测过两个 agent 并发写同一个仓库，六次写入里五次曾经消失，原因就是抢 `.git/index.lock` 抢输。
- **共享 + CRDT 实时同步**：实测过的一次合并完全合法、一个字符都没丢，但结果是错的。更根本的理由是 **agent 需要稳定的世界** —— 它的循环是"读 → 判断 → 改 → 再读"，中途文件被对方改了，它的判断就悬空了。
- **一个项目一棵树**（所有人共用一棵）：冲突的定义是"两个独立写入者的改动要交汇"，同一个人的两条对话线不是两个写入者 —— 用它会把这个定义用错对象。
- **一个显式的"开一条隔离会话"开关**：回滚本身就是那个能力，每个 checkpoint 就是一个"试之前"的位置，不需要再加一个开关。

## 代价与换来的

- **没有任何"自动发现对方在改同一个文件"的机制** —— 没有文件锁，没有实时共享。这是有意的：两个人在同一个文件上盲撞，留到合并时暴露。
- "实时看到对方在干什么"的载体从**文件系统同步**变成了**事件流 + diff**。严格说这不是体验降级，但它和最初设想的画面不一样。
- 同一个人的两条会话不能同时跑（租约按树算）。
- 换来的是：agent 在一轮之内的世界是稳定的、每一步可回滚、改动有审计，而且"合并"只在人点的时候发生。
- **主干是只读的**：谁都不在自己的树里直接改主干，改它只有"合并"这一条路（而合并要拿项目级的那把锁）。这一条让"主干上永远是可运行的代码"成为结构性的保证，而不是纪律。
- **"每人一棵完整的树"就是"能服务多少用户"的硬顶**（磁盘占用 + 每棵树的初始化时间），它排在内存和连接池之前。真要做容量，替代方案是"配额 + 空闲回收"或者"共享对象库"，但那两样都得**先量再定** —— 现在没有数据，所以没做。

## 什么情况下该重新考虑

如果产品要三个以上的人在同一项目里并发干活（现在是硬上限 `MAX_MEMBERS = 2`），或者"实时看到对方的每一次按键"变成真实需求 —— 那时要重新设计并发模型，而不是加一个开关。
