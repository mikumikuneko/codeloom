# 决策：代码检索用 grep/glob，不做 RAG

## 是什么问题

agent 要在别人的仓库里找东西。给它什么？向量检索（把代码切块、算 embedding、按相似度召回）还是老老实实的精确匹配？

## 定了什么

两个工具：`grep`（按正则搜内容）和 `glob`（按模式列路径），都是精确匹配，不建索引、不算 embedding。给模型的说明里也是这么写的。

## 还考虑过什么，为什么没选

- **embedding + 向量库**：代码检索要的是**精确**，不是**相似** —— 找的是一个标识符、一个字符串、一处调用，不是"意思差不多的东西"。向量召回会把"看起来像"的结果端上来，而 agent 需要的是"确实存在的那一处"，在此基础上它自己判断。
- **先 glob 再 grep 的"两段式检索"**（我们现在的做法）：`glob` 先按路径筛掉不该看的（比如 `node_modules`、`target`），再在剩下的文件里搜 —— 一个带依赖目录的仓库动辄十万个文件，直接全量枚举再丢弃 99% 是白花的。
- **建一份代码索引**（调用图、符号表）：那是 LSP 的活，成本高得多，而且只在"语言服务能起来"的项目上成立。

## 代价与换来的

- 模型得自己写正则/glob 模式；写歪了就是搜不到（不会"模糊地"给点东西）。
- 大仓库里一次 grep 可能要枚举很多路径 —— 所以才有上面那个先 `glob` 筛路径的做法。
- 换来的是：结果可解释（"我按这个模式搜的，命中这些"）、零索引维护、零外部服务依赖。
- `glob` 的匹配是**自己写的正则**，不用 JDK 的 `PathMatcher`：后者的 `**/` 是"**至少一层**"，和 bash、.gitignore 的语义不同 —— 于是 `src/**/*.java` 这种（写在工具说明里的例子！）什么也匹配不到。工具的模型是"用过 glob 的人都懂的那个"，所以跟着 bash 的语义走。

## 什么情况下该重新考虑

如果将来要做的是"按意图找代码"这种模糊查询（比如"找出所有处理重试的地方"），那是**另一个工具**该干的事，不该拿它替掉 grep。
