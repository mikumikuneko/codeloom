# 决策：六边形 + 战术 DDD + 事件溯源，明确不是 MVC

## 是什么问题

这套系统整体是什么形状？面试第一句通常就是"你的架构是什么"，而这个答案会决定后面所有切片方式（模块怎么分、规则住哪儿、依赖指向谁）。

## 定了什么

三个名字，各管一件事：

- **六边形（端口与适配器）**：领域不依赖框架。`domain` 模块零依赖，上下游通过端口（`EventStore`、`ExecutionLease`、`WorkspaceManager`）对接，适配器住在别的模块里。含羞的细节是**依赖方向由编译器强制** —— 不是靠纪律。
- **战术 DDD**：聚合根、值对象、领域事件这些具体的模式（`Session`、`SessionId`、sealed 的 `Event` 层级）。
- **事件溯源**：事实以事件形式持久，状态是折出来的（见"只建一张事件表"那篇）。

**明确不是 MVC**（没有"controller 直接操作数据行"的那条路），**战略 DDD 是弱的**（只有一个业务域，没有限界上下文可划，硬划是自欺）。

## 还考虑过什么，为什么没选

- **分层 MVC**（controller → service → repository，实体是贫血的数据行）：最快能跑起来，但领域规则会散进 service。而"规则有地方住、并且能讲清为什么"正是这个项目要展示的东西。
- **纯 DDD（含战略设计与限界上下文）**：一个业务域谈限界上下文，是把术语用在自己身上而不解决任何问题。
- **只做事件溯源、不做六边形**：那事件流会和 ORM、Web 层缠在一起，而"领域能纯单测"是后面很多取舍得来的前提。

## 代价与换来的

- 每个能力都要写端口 + 适配器；领域对象与数据行之间要多一层映射（四张表，代价还算小）。
- 换来的是：依赖方向不靠自觉、`agent` 模块可以完全不碰数据库地单测、以及**每个"为什么"都有地方落**（这套决策记录本身也是它的一部分）。
