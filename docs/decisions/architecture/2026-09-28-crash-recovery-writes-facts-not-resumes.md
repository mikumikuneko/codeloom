# 决策：崩溃恢复只补写事实，不自动接着跑

## 是什么问题

平台中途挂了（进程被杀、机器重启）。重启之后，那些"跑到一半"的会话怎么办 —— 自动接着跑，还是等有人说话？

## 定了什么

只**补写事实**：把悬着的调用收成一个终局状态（"被打断"或"没跑完"），让事件流自洽、让下一轮能正常继续，然后停下。**不自动续跑。** 这条和"审批之后接着跑"不是一回事 —— 后者是必需的（那一轮本来就是等人批才停的，答复一到就该走），而它不追加用户消息。

## 还考虑过什么，为什么没选

- **自动续跑**（用一个开关控制）：它唯一真有价值的场景是**无人值守的服务** —— 容器或服务管理器自动重启，那边没有人会说"继续"。我们是"宿主机上跑、人在键盘前"的形态，那个场景不存在。
- **顺带做一份"token 账本"**（区分哪部分 token 是平台替你花的）：它依赖的前提是"平台在替用户花钱"，而这个项目是 BYOK —— 用户拿自己的 key 付款，没有平台的钱，"分清哪笔是平台的"也就没有对象。整个账本连着它的字段一起删了。

## 代价与换来的

- 崩溃之后要人自己说一句"继续"（界面上会看到那一轮是"被打断"结束的）。
- 换来的是：不会在没人看着的时候自动烧掉用户的额度，也不会把一堆半成品接着往下跑；而事件流仍然是自洽的 —— 恢复只需要"补写事实"，不需要"猜意图"。
- 恢复的具体边界要写清：`ToolApprovalRequested` **从待补名单里划掉**、`ToolApprovalResolved(approved)` **加回** —— 不然重启会把"正等人批"这种正常状态修成"失败"。这一条如果反了，症状是"批准过的会话一重启就废"。
- 另一条代价一并记着：删掉 `DONE` 这类终态之后，恢复要扫**全部**会话。如果当初留下"自动续跑"的开关，那意味着**每次重启对每一条空闲会话发一次付费的模型调用** —— 那个开关删掉才是对的。
