# 决策：租约服务够不到就说"够不到"，续约失败一律等于失去执行权

## 是什么问题

两个中间件里任何一个挂掉，租约这条路上会怎样？读代码读出来两个事实：

**一、拿锁时的连接失败，外面看起来像我们的 bug。** `tryAcquire` 里那次 `SET NX PX` 抛的连接异常，从执行器一路穿到接口层，落到 **500**。而 500 说的是"我们坏了"，客户端据此去查缺陷 —— 正确的处置其实是稍后再来。

**二、续约调用抛异常这条路径没人接。** 看门狗是这样写的：`renew` 返回假 → 判定失去执行权、取消本轮。可 `renew` 本身是一句 `redis.execute(Lua)`，**Redis 中途挂掉时它抛异常** —— 异常从那条虚拟线程里冒出去，线程安静地死掉，而"失去执行权"这个标志**永远是假**。于是这一轮**以为锁还在**，照常跑完。

第二条尤其别扭：`renew` 自己的注释写着为什么"续约失败"必须立刻停 —— 后续写入有 fencing token 挡着，**但工作区里那些改动没有任何东西挡**。返回假要停，抛异常却没人管，而抛异常恰恰是更常见的那一种。

**三、还锁失败会盖掉本轮的结果。** 释放锁那一句站在 `finally` 上，而它原来会把 Redis 的异常直接抛出去 —— 那样一来，调用方看到的不是"这一轮跑成了还是失败了"，而是"还锁的时候连不上"。**结果比还锁重要得多。**

## 定了什么

**三处，都在"失败要说清楚"这一侧，没有降级。**

- 看门狗把续约时**抛出的异常当成"续约被拒"**，走同一条路：判定失去执行权、取消本轮、打一条 warn（把原因留在日志里，不然这条路径是无声的）。
- 连接失败被翻译成一个领域事实：`LeaseUnavailableException`（在端口上，和 `StaleLeaseException` 并列），由 Redis 适配器抛出、接口层映射成 **503**。
- **`release` 的契约改成"不抛异常"**（端口上写明，实现负责记日志）。它还不上不要紧 —— 锁有 TTL，最坏是别人多等一个 TTL；而它在 `finally` 上抛出去，盖掉的是本轮真正的结果。

**拿不到锁就是跑不了** —— 无论是因为别人拿着（409 那一类），还是因为问不到（503 那一类）。这两个码分开，是因为客户端该做的事完全不同。

**MySQL 那边不做任何事**：写不进去就是这一轮没有发生过。事件流是唯一真相，"先攒在内存里稍后补写"等于把这句话破掉。

## 还考虑过什么，为什么没选

- **降级成"没有锁也跑"**：绝对不行。写入还有 fencing token 挡着，**但工具在磁盘上的改动没人挡** —— 两个实例同时跑构建会互相踩，而那正是这棵树的工作树隔离本来要防的事。
- **降级成"单实例模式"**（Redis 不可用时假定只有自己）：我们**没有依据**知道是不是只有一个实例。一个猜错的假定比一个明确的失败坏得多。
- **把"问不到"和"没抢到"合并成一个返回值**：那会让客户端把"中间件挂了"读成"别人在用"，然后去等等看 —— 而真正该做的是退避重试。
- **只在接口层 catch 一下给 503**：那要 web 层去认识 Redis 的异常类型，而"这把锁现在问不到"是个**领域事实**，不是 web 的事。
- **只在调用方的 `finally` 里各包一层**：调用方不止一个（跑一轮、丢会话、合并、崩溃恢复都站在 `finally` 上），每处各包一层就是同一件事写五遍、漏一处就漏一处；而"还不上不该惊动调用方"本来就是**这个端口**的性质，写在端口上，实现就只有一处要守。

## 代价与换来的

- 代价：多了一个异常类型，以及"适配器要把中间件的失败翻译成领域事实"这一层责任。
- 代价：Redis 抖动会**比以前更早地中止**正在跑的一轮 —— 以前那种情况下它会默默跑完。这是故意的：默默地跑完意味着它可能在一个已经不属于自己的工作树上继续改文件。
- 换来的是："失去执行权就停"这句话在**续约调用本身失败**时也成立，而不只在续约被拒时成立。
- 换来的是：中间件挂掉时，用户拿到的是一个能理解、能据此重试的 503，而不是一个看起来像缺陷的 500。

## 什么情况下该重新考虑

如果哪天真的要多实例容忍中间件故障（比如 Redis 集群整体不可用时宁可只读），那要讨论的是"只读形态"长什么样，而不是把"没有锁也跑"重新搬回来。
