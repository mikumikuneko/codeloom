# 决策：压缩先看一手读数，离水位远就不读整条流

## 是什么问题

"要不要压缩"每轮都要算一次，而它算的方式是**把整条事件流读回来、重新投影、数字符**。会话越长这一趟越贵，而它每轮都做一遍 —— 哪怕绝大多数轮次的结论都是"还早，什么都不用做"。

那个判断本来就有两个输入：一个是按字符估的，一个是**服务商上一轮亲口报的**。前者照英文的四字符一 token 算，对中文只会偏低；真正拍板的通常是后者。也就是说：更准的那个数我们早就有了，却每轮把它连同整条日志重新推一遍。

## 定了什么

`EventStore` 多一个 `lastContextTokens(sessionId)`：一次点查，取这条会话最后一条带读数的 `TurnTokensUsed`。

`ContextCompactor.compactIfNeeded` 在**按压力判**那条路上先看它：有值、又低于微压缩水位，这一轮直接返回，不读历史。问不出来（新会话、或最后那次收尾没有读数）或者越过水位，就照老路把整条流读回来算一遍 —— 那条路是权威判据，一个字没改。溢出那条路（`Trigger.OVERFLOW`）根本不看阈值，也不经过这道闸。

## 还考虑过什么，为什么没选

- **让压缩器改用那条活投影**：能省掉读库和逐条解码，但每轮仍要把 N 条消息走一遍数字符；而且投影要多留两份派生状态、多三个访问器。收益小、改动大，留着等上下文长期贴着水位时再说。
- **在内存里记着上一次的读数**：少一次点查，但多实例下会拿到**别的实例写的、或者过期的**数 —— 而过期的方向是"以为还很空"，正好错在不安全那边。点查读的是库里真实的最后一条，没有这个问题。
- **把 SQL 写成过滤 payload 里那个字段**（一次就取到"最后一条**有读数**的"）：那等于让 mapper 去认 payload 的内部形状，而形状归编解码器管。

## 代价与换来的

- **代价之一**：最后那次收尾没有读数时（一轮被取消）问不出来，那一轮退回老路读一遍。一次取消换一次全量读，且下一次收尾就又有了读数。
- **它不是"取大者"那个判据的近似**，说清楚它差在哪：旧判据是 `max(按字符估, 读数)`，短路只看读数，所以两者分道扬镳的唯一情形是**按字符估比读数还大**（那时旧代码判"该压"、短路不判）。而按字符估照英文定、**对中文只会偏低**；要判反，得服务商报出一个比"字符数 ÷ 4"还小的数。
- 剩下那点差由压缩点自己那段窗口兜着：它跑在一轮**开始**、用户那句话**还没落库**，中间只落两条状态变更事件（重试回 IDLE、进 THINKING）—— 那些不进上下文，投影输出和上一次读数时**逐字节相同**。
- **换来**：绝大多数轮次从"读整条流 + 逐条解码 + 重投影 + 数字符"降到**一次点查**。

## 什么情况下该重新考虑

压缩点前面哪天开始落**会进上下文**的事件（比如每轮加一条系统提示），那个窗口就不再是空的，这道闸要跟着改成"读数 + 那几条的估算"。或者上下文长期贴着水位、每轮都在真算估算时，再上"复用活投影"那一条。
