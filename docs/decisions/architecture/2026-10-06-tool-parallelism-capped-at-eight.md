# 决策：一轮里并发跑的工具调用封顶 8 个

## 是什么问题

模型一次给出多个工具调用（读几个文件、搜几处），我们并发跑几个？让它们全跑？还是排着队跑？

## 定了什么

上限 8（`MAX_PARALLEL_TOOLS`，用一个信号量控制），一批里多余的排队。

## 还考虑过什么，为什么没选

- **不设上限**：同一台机器上还跑着别人的轮次。模型一次给出二十个调用就能把机器占满 —— 而"一次给二十个"恰恰是模型很常见的写法。
- **照抄某个本地 CLI 的默认值**（10）：那是**本地 CLI**，一个用户一台机器、跑不动也是他自己等；我们是服务端，机器是共用的。上限要有，而且理由和它们不同。
- **一次只跑一个**：读文件的场景会白等（本来可以并行的 IO）。

## 代价与换来的

- 极端情况下（一次二十个调用）比全放开慢一点。
- 换来的是：同一台机器上多个会话之间有个基本公平 —— 一个会话不会因为模型写了二十个调用就把别人挤没。
