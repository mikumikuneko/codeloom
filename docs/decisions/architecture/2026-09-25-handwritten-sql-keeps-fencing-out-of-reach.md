# 决策：mapper 全手写 SQL，不继承 BaseMapper

## 是什么问题

`fencing_token` 这一列是"锁失效之后，过期持有者的写入被拒绝"的落点。它绝不能出现在普通写入路径里 —— 那么，靠什么保证它不会被顺手写坏？

## 定了什么

所有 mapper 都手写 SQL，**不继承 `BaseMapper`**。`fencing_token` 只出现在它该在的那几条语句里（推号和 `assertValid` 的比较），不在别的任何 `INSERT`/`UPDATE` 里。

## 还考虑过什么，为什么没选

- **继承 `BaseMapper`**（`insert` / `updateById` 按实体字段逐个写列）：那样 `fencing_token` 会跟着实体一起被写进去，而"这次写入有没有动那一列"从代码上看不出来 —— 更要紧的是，漏写或者误改都**不会被发现**。写成显式 SQL，那一列根本不在语句里，"没碰它"这件事是看得见的。
- **只用 `LambdaQueryWrapper` 之类的条件构造器**：同样的道理 —— 列名不出现在代码里，就没有"我碰了哪几列"这个可读的证据。

顺带记一笔：依赖里曾经声明过 MyBatis-Plus，后来发现全项目一行它的 API 都没用上，删掉了，换成裸 MyBatis + `mybatis-spring`。

## 代价与换来的

- 每个字段、每次增删列，SQL 都要自己改（没有自动映射兜着）。
- 换来的是 fencing 那条不变量有了一个**机械的落点**：安全上最要紧的一列，不在同一个"万能写入"的射程里。

## 什么情况下该重新考虑

如果将来这张表字段多到"手写 SQL"成为主要维护成本，可以考虑生成，但生成出来的 SQL 仍要能一眼看出"这一列在不在语句里"。
