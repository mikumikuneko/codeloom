# 决策：虚拟线程，不上反应式

## 是什么问题

一轮里绝大部分时间在等：等模型吐字、等子进程结束、等 Redis。这种"全是等待"的负载，用反应式栈还是用线程？

## 定了什么

**Java 21 的虚拟线程 + 同步阻塞的写法**（`spring.threads.virtual.enabled=true`）。一轮的代码就是一条直线：调模型、跑工具、落事件 —— 没有回调、没有操作符组合。

## 还考虑过什么，为什么没选

- **WebFlux / Reactor**：等待确实适合异步模型，但代价是整条链路（HTTP → 用例 → 模型流 → 子进程）都要变成流式组合子；调试栈断成碎片，异常传播也要重学一遍。而我们的并发量根本不是这个量级的瓶颈。
- **固定大小的线程池**：等模型的时候线程全被占住，池子大小直接变成"同时能跑几轮"的上限 —— 而想调这个上限又不敢调（线程是昂贵资源）。
- **把等待外包给消息队列 / 任务引擎**：那是把"一轮的状态机"折成两半，回放和取消都要跨进程，代价远大于收益。

## 代价与换来的

- 依赖 JDK 21；虚拟线程也有它自己的注意事项（少数 pinning 场景）。
- 换来的是：**用同步代码写出异步吞吐** —— 一轮在代码上是一条直线，能读、能断点、能贴进报告；子进程那个"两个流各起一个虚拟线程去读"的写法也是白送的（见 `ProcessRunner`）。
