# 决策：列表分页用 offset，不用游标

## 是什么问题

"我的会话""项目列表"这类接口怎么翻页？用 `offset/limit`，还是用一个"从上次那个位置继续"的游标？

## 定了什么

`offset` + `limit`（默认 `0` / `50`，"跳过多少条"为负数时按 0 处理 —— 数据库的 `OFFSET` 不接受负数）。

## 还考虑过什么，为什么没选

- **游标分页**：它的长处是"只追加"的数据（翻到第二页时第一页不会变）。这两个列表**不是只追加**的：会话会被丢弃、项目会被退出，所以游标并不能给出一个稳定快照，却要多维护一个不透明的游标参数。
- **一次全量返回**：成员上限和会话数量在开发阶段都不大，但接口的形状不该建立在"现在数据少"上。

## 代价与换来的

- 翻页时代内容会变（丢弃一条会话，第二页就会往前挪一格）—— 对"我的项目/会话"这种列表是可以接受的。
- 换来的是：接口最简单、能直接跳到任意页、前端也不用管游标的生命周期。
- 这条决策踩过一个坑，记下来：事件接口默认 200 条、上限 1000，而回滚面板一开始**不带分页参数**去取 —— 于是长会话的回滚面板只看得到**最早 200 条**。它的修法不是加参数，而是**面板不再走那个接口**（改成读客户端已经折好的那份）。"默认值"就是接口的行为，忘掉它就是 bug。

## 什么情况下该重新考虑

如果哪一类列表变成严格只追加、而且量级很大（比如某个全局审计流），那时游标才是对的选择。
