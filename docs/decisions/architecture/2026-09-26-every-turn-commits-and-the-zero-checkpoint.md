# 决策：每轮结束显式提交，建会话时落下第 0 个检查点

## 是什么问题

agent 改了一堆文件，什么时候把它们落成一次 git 提交？以及：一条会话刚开始、还没跑过任何一轮的时候，要不要有一个"可退回的位置"？

## 定了什么

- **每轮结束显式提交一次**（哪怕这一轮什么都没改）。
- **建会话时落下第 0 个检查点** —— 它在事件流里的第 0 条之后，记的是**这棵树当时的位置**。

## 还考虑过什么，为什么没选

- **只在"真有改动"的时候提交**（少写几条空提交）：那样 agent 的产出对 git 是**未跟踪的** —— 分支上没有那笔提交。后果是三件事同时坏掉，而且**全程不报错**：合并时"合了个寂寞"（对方的树上看不到你的东西）、回滚时"什么都没回滚"（因为改动根本没进版本库）、"这一轮改了什么"要靠另一套机制去数。宁可多几条空提交，也不能让"改动的载体"不存在。
- **把第 0 个检查点省掉**（"反正会话还没动过"）：不行 —— 每轮结束才打下一个检查点，没有第 0 个的话，"撤销第一轮的全部改动"就没有可回的点，而那是回滚最常用的那一次。
- **让用户点一下才提交**：那"提交"这件事就变成用户的负担，而且忘点一次就丢一轮的可回滚性。

## 代价与换来的

- 历史里会出现"没改什么"的空提交（同步和合并会带着它们走）。
- 第 0 个检查点记的是"树当时的位置"，所以**同一个人的第二条会话**"撤销全部改动"退到的正是"我开始说话之前"——那是对的：换会话本来就不该把代码退回去。
- 换来的是：回滚和合并这两个功能**有东西可操作**；"这一轮改了什么"也有了一个天然的边界。
