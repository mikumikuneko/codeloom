# 决策：装配历史那一个只有一个，配置只在装配它的地方定

## 是什么问题

"把一条会话的事件流装配成发给模型的消息"（`ContextAssembler`）上有一层配置：**按 id 查用户名**。装上它的那份，别人捎来的留言会写明**是谁**说的（`[来自 小李 的 agent 的留言]`）；没装的那份只会说"协作者"。

从前有没有这层由**两个调用方各自决定**：投影那份装了，压缩器那份没装 —— 而压缩器装出来的东西有两条出路，其中一条**会被写进摘要、顶替整段历史**（另一条是数字符估 token，那条本来就不在乎名字）。于是压缩一次之后，模型再也分不清那条留言是谁提的，而那个事实**只会活在摘要里**了。

它不报错，也没有任何地方会提醒。而当时那段代码还写着"没有查名字这一层时的装配器（测试、以及任何不关心留言来源的调用方）"—— 压缩器**是在乎的**，它只是漏了。

**危害要如实说轻**：丢的是"是谁"，不是"这是别人捎来的"—— 标注本身还在，所以"别把别人的请求当成自己用户的"那条安全属性仍然成立。真正值得动手的理由是**结构上的**：一个静默的降级配置能被生产代码走进，而走进去时没有任何信号。

## 定了什么

- 装配器收成一个 `@Bean`（`ContextAssemblyConfig`），**配置在那里定死**；`SessionProjections` 和 `ContextCompactor` 都注入它。它住在 app 而不是装配器自己那个模块里，因为那边不带 Spring。
- **`ContextAssembler` 不再有"不要名字"的构造函数**：每个调用方都必须说出名字从哪儿来，不要名字的地方明写 `id -> null`。这条同时是既有决策的必然结果 —— `simplification/2026-10-04-members-that-only-tests-use.md` 说"只给测试用的生产成员一律移走"，判据是**数生产代码里的调用点**；改完无参构造的调用点是 0。
- 压缩器里那两个内部换算（按字符估 token、装摘要输入）从静态变成实例方法 —— 它们于是拿到的是**同一个**装配器，不再有"这里用哪个"这个问题。
- 顺手把"喂给摘要模型的那份输入"提成一个具名方法（`summaryInput`）：它装出来的东西会顶替整段历史，值得有个名字说明这件事。

## 还考虑过什么，为什么没选

- **就地修**（压缩器自己 new 一份带名字的）：修掉这一处，但那个表达式（`id -> users.findById(id).map(User::displayName).orElse(null)`）就出现在两处 —— 下一个要装配历史的调用方照样能再造一份，而"同一个概念有几套配置"又回来了。
- **只把注释改准**（写明无参构造只给测试、以及不产出发给模型输入的地方）：诚实，但降级模式还能被悄悄拿到。
- **给无参构造换个具名工厂**（`withoutDisplayNames()`）：那正是"只给测试用的成员"，刚被那条决策删过。
- **那个 `@Bean` 只包在 `ContextCompactor` 里**：见上面第一条，那还是第二个配置点。
- **数字符估 token 那一处继续用不带名字的**：那样压缩器里就有两份装配器，而"这一处用哪份"又要每次判断一遍 —— 名字对估算只差几个字符，不值得留这个口子。

## 代价与换来的

- 代价：多一个 `@Configuration`；压缩器那两个换算方法从静态变成实例（几处测试跟着改）。
- 代价：**`@Bean` 里那个查名字的表达式本身没有测试** —— 它是一行查找，行为和投影这边原来那句逐字相同；测它需要一个 Spring 上下文，而它出错的方式（查不到名字）已经由 `MessageFold` 的兜底接住了。测试守的是**"压缩器那条路真的带上了名字"**，不是那句查找。
- 换来："装配器配成什么样"不再是一个每个调用方都要重新回答一遍的问题；那个静默降级模式**在类型上就不存在了**（没有无参构造可走）。

## 什么情况下该重新考虑

如果哪天出现第二个**真的需要不同配置**的装配场景（比如"给界面看的装配"要另一种取舍），那就不该硬塞进同一个 bean —— 到那时"配置只有一处"这条要按用途重新划，而不是把两个用途挤成一个。
