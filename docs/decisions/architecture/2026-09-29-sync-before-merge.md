# 决策：先同步主干再合回主干，另给一个独立的"同步"按钮

## 是什么问题

合并的方向：把自己的改动**合回主干**，还是先把**主干同步进自己的分支**？顺序不同，冲突发生在谁的树上就不一样。

## 定了什么

**先同步（主干 → 我的分支），再合回（我的分支 → 主干）**。

配套两条：合并前做**过期检查**（"我出发之后主干动过没有"，放在项目锁里查）；另外给一个**独立的"同步"按钮**。

## 还考虑过什么，为什么没选

- **先合回再同步**（"分支 → 主干，冲突在主干的临时工作区里解决"）：冲突会在**公共的主干**上解决，而且"我的代码先落地、再拉回来"会让主干有段时间带着别人还没同步的改动。
- **只做合回、不给同步按钮**：少了"提前看看会不会撞"的能力 —— 而更重要的是，同步还有一个**语义**上的用处：把对方的代码带进我自己的树里，我 agent 下一轮 `read_file`/`glob` 就看得见它，**它有机会自己发现"咦，我已经有个 `LoginService` 了"**。
- **把同步当成一个回滚点**：回滚点的定义是"代码位置 + 对话位置**成对**"，而同步不推进对话 —— 单独成点会让回滚列表里出现一堆"对话没动"的条目。

## 代价与换来的

- 合并变成两步（加上人裁决可能更多），而且**两步之间不原子**（中间要等人裁决，可能几分钟）—— 所以要有**过期检查**兜着：那一步失败时的措辞是"你出发得早、别人先到了"，而不是"你们的代码打架了"（后者会误导人）。这个区别很重要：大多数时候根本没人打架。
- 换来的是：冲突在**各自的分支上**解决（主干永远干净可运行）；而且同步顺带成了"发现重复劳动"的一条通道。
