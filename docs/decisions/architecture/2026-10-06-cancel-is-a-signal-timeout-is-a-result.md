# 决策：取消是信号，超时是结果

## 是什么问题

用户按 Esc，那一轮什么时候停？命令卡住了等多久？以及停下来的那一次，算成功、算失败、还是算第三种东西？

## 定了什么

取消是**信号**，检查点在**工具边界**上（每次模型调用前、每个工具调用前）。命令执行处按 100 毫秒一段轮询取消信号，一旦发现就**先杀掉整棵进程树再返回**。前端按 Esc 之后不假装已经停了，状态行上如实显示"正在停…"。

超时**不是异常**，它和"被杀"一样是返回值的一部分（`CommandTermination.TIMED_OUT` / `CANCELLED`）：半截输出照常收回来，判"这条命令算不算成功"看 `termination()`，**不看退出码**。被杀掉的命令退出码可能是 1 这种占位值。

## 还考虑过什么，为什么没选

- **立刻掐断**（读到一半就杀）：会留下不一致的状态，而且"跑完手上这个工具再停"最多多等几秒 —— 这个取舍是明确的。
- **把超时当异常抛**：会把已经拿到的输出一起丢掉，而那些输出正是要看的东西（一条超时的构建，报错信息通常已经在里面了）。
- **协作式超时**（让工具自己响应"到时间了"）：我们的"工具"是一条 shell 命令，不是我们的代码，它不会跟我们合作。
- **把"被杀"折进退出码**：退出码和"怎么结束的"是两根轴，折在一起会让"超时的合并"被读成"有冲突"（那条命令的退出码恰好也是 1）—— 后果是让人去解决一堆不存在的冲突。

## 代价与换来的

- 按下 Esc 之后到真正停下之间还有最多几秒；界面上必须如实说"正在停…"，否则按的人以为键没生效。
- 判据变复杂一点（任何"成功了吗"的判断都要同时看两根轴）。
- 换来的是：停下来的那一刻状态是自洽的，半截输出不丢，而"超时/取消/失败"三件事在事件流里是三种不同的事实。
- **同一族的另一条**：模型调用的重试也从 provider 客户端**搬回了循环**，退避前先落一条 `LLM_RETRY_SCHEDULED`。留在客户端里的重试有两个坏处：睡的那几秒按 Esc 没人理，而且那几次失败在会话日志里看不见（自己的注释早就写着"该重试还是该提示用户，上层更清楚"，是代码违反了它）。服务端给的 `Retry-After` 两者都认（秒数和 HTTP 日期）。
