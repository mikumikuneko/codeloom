# 决策：命令收一整行，写进临时脚本交给 bash

## 是什么问题

模型给出一条命令，我们怎么把它送出去？收一个参数数组、还是收一整行字符串？中间要不要过一层 shell？以及 —— 这台机器上没有 bash 的时候怎么办？

## 定了什么

`RunCommandTool` 收的是**一整行命令字符串**。执行时把它写成一个临时脚本文件，用 `bash <脚本路径>` 跑（`CommandShell`），**不是** `bash -c "整串"`。命令里不能有回车。只认 bash —— 不认 `sh`，也不降级到别的 shell；这台机器上找不到 bash 时，只让"跑命令"这件事失败，不让整个应用起不来。

顺带改了一处判定：路径守卫原来是靠解析 argv 来判断"这次 `rm` 会不会删到项目外面"，命令变成整行之后那个判断没了 —— 所以改成保守判定：会改文件的命令里带路径的一律要问人，**认不出来的一律当作"可能在树内"**。

## 还考虑过什么，为什么没选

- **收参数数组、不过 shell**（最初的设计，也确实实现过）：模型的词汇里就没有管道、重定向、`&&`，报错是"无法启动进程"这种和真实原因无关的话；而且"同一行命令在不同启动方式下结果不一样"本身就是个 bug。改成整行换来的代价写在下面。
- **`bash -c "整串"`**：实测过三种送法，`bash -c` 会把参数位置错开（`$0` 被吞掉、输出还少了几行），只有临时脚本文件是原样到达的。
- **把命令喂给 stdin**（`bash -s`）：脚本自己占着 stdin，脚本里任何读标准输入的命令（`cat`、`read`）会把脚本剩下的部分吃掉。
- **接受 `sh`**：`sh` 的语义比 bash 窄，我们写出来的命令会按"最小公倍数"来约束，得不偿失。
- **降级到 PowerShell**：那会让"同一行命令"在不同平台上语义完全不同 —— 而命令是模型写的，它没法同时猜两个方言。
- **找不到 bash 就直接退出进程**：我们是个 Web 应用，还有聊天、看代码这些根本不依赖 shell 的功能，为一个路径配错就让整个服务起不来，不划算。

## 代价与换来的

- 这台机器上必须有 bash（Windows 上就是 Git Bash）。
- 每条命令多一次临时文件的创建与删除；`$0` 是脚本路径而不是 `bash`。
- 多了一条"命令里不能有回车"的检查。
- 换来的是：模型的命令词汇是完整的（管道、重定向、`&&` 都能写），而"参数错位"这类诡异失败不会发生。
- 另记两处细节：① 这里对齐的是**语义**（"模型写的是一整行、我们照着跑"），不是某种传参方式；实测里真正有损的只有**双引号**这一种情形（空格、单引号、中文在 `bash -c` 下都是好的）——所以"凡是文本进参数表就不可靠"是一句过头话。② bash 的查找链路是"配置 → 环境变量 → PATH → 顺着 `git.exe` 上找 → 几个常见位置"，**不写死盘符**：Git for Windows 默认只把它的 `cmd` 目录放进 PATH，所以"PATH 上找 bash"在默认安装的机器上找不到。
