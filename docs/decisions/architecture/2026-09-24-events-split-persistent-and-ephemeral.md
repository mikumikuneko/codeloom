# 决策：事件分两类，逐 token 的增量在编译期就落不了库

## 是什么问题

流式生成时，模型一个 token 一个 token 地吐字。这些增量要不要进事件表？如果"不该进"这件事只写在注释里，它能守住吗？

## 定了什么

`Event` 这个 sealed 层级分两支：**`PersistentEvent`** 和 **`EphemeralEvent`**。追加事件的方法（`EventStore.append`）**只收前者** —— 逐 token 的增量是后者，想落库**编译不过**。

## 还考虑过什么，为什么没选

- **一个 `Event`，加一句"delta 不要落库"的注释**：那种纪律会在某次重构里悄悄失效，而症状是 event 表每轮涨几千行 —— **数据量小的时候完全看不出来**，等看出来时历史已经脏了。
- **全部落库**（"反正断了能补齐"）：表会被 token 级噪声淹掉，回放也没意义 —— 增量不是事实，合成后的那条消息才是。
- **用运行时检查挡**（存之前判断一下类型）：能挡住主路径，但"能不能写"这件事在编译期就该有答案。

## 代价与换来的

- 编解码要认两类（Redis 那条推送线两类都要能解），而且从表里读出一行时还要再挡一次（防手工 insert 绕过编译期）。
- 换来的是：**误落库在编译期不可能发生**。类名本身就把"这是易失的"说清楚了，读代码的人不用去翻注释。
