# 决策：Redis 不做缓存

## 是什么问题

"项目用了 Redis"后面通常会跟一句"那缓存放 Redis 吧" —— 多实例、共享、自带 TTL，看着是现成的。

这件事当时没写下来：折到一半的结果放哪，是跟着投影那篇一起定的，Redis 一个字没提。问题是在那之后被问出来的，这篇就是那个答案。

## 定了什么

Redis 在这里只做**协调与投递**，一个"下次直接取"的键都不存：

- **执行租约** —— `codeloom:workspace-lock:` 下的键，`SET NX PX` 抢锁，两段 Lua 做续约与释放（`RedisExecutionLease`）。
- **事件总线** —— 所有会话共用一条频道，本实例的订阅者也绕一圈 Redis 回来（`RedisEventBus`）。
- **中断信号** —— 一条独立频道，把"停"送到正在跑的那一轮（`RunningTurns`）。
- **待投递的 agent 笔记** —— List 当队列，另有一条 pending 做搬运（`AgentNotes`）。
- **登录会话** —— Spring Session 的存储，每个请求都要读写，五样里它最像缓存。

项目里唯一够格叫缓存的是 `SessionProjections`：会话那条活着的投影，住在**进程内存**里，按访问顺序淘汰，上限取条数与字节先到的那条。

判据只有一句：**丢了会不会算错**。上面五样丢了都会算错（租约没了两个人能同时跑同一棵树、事件丢了界面显示的就是假的、会话丢了要重新登录）；投影丢了只是重算一遍。缓存是后一类。

## 还考虑过什么，为什么没选

**把这台实例当缓存用。** 它的 `maxmemory-policy` 必须是 `noeviction`（理由见 `redis-lock-needs-noeviction` 那篇：租约住在这儿，被淘汰等于锁凭空消失），而**缓存与不淘汰是互斥的** —— 写满时它报错、不淘汰最久没用的键。那已经不是缓存，是一个写满会让服务开始失败的内存库。真要用它缓存，只能另起一个实例，为一个可有可无的东西多一个中间件。

**把会话投影放 Redis，让多个实例共用一份。** 投影在一轮里是**活的**：调用方拿着那个对象继续往上折新事件，不是一份冻结的值。放 Redis 等于每迭代一次序列化一整棵投影再加一次往返，而"真正的开销在反序列化和重放"正是要省掉的那一半。何况也没有共用它的需求 —— 同一棵树同一时刻只有一个执行者，跨实例的可见性由"事件流 + 往后补读"解决，用不着在第二个地方存同一份东西。

## 代价与换来的

- 亏的是：投影只活在单个进程里，进程重启后第一条会话要重建一遍；多实例下各存各的。
- 换来的是：Redis 的角色窄到一句话能说完 —— **锁、通道、队列、会话**，四样都不承担"加速读"。于是它写满时的行为是确定的（报错），不会以"某个缓存被淘汰了"的形式，表现成一次极难复现的正确性事故。

## 什么情况下该重新考虑

出现"每个请求都要重算、结果与谁都无关、过期了也无所谓"的读放大时 —— 那才是一个够格进缓存的负载，而且它该进的是**另一个** Redis 实例，不是这一台。
