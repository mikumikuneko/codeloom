# 决策：待定回声做成可注入的状态机，全应用那一份留着

## 是什么问题

"我刚发出去、还没在流里看见的那句话"要有个地方存：输入框（`Composer`）在请求发出**之前**把它记下来，会话流（`SessionStreamView`）在流里多出一条用户消息时把它收走。这段逻辑从前是一组**模块级的表和函数**（`echoes` 那个 Map + 三个导出函数）。

两个麻烦：

- **它测不了。** 状态只能通过 `usePendingEcho` 这个 React hook 读出来 —— 想测那条回收规则就得引 jsdom 和 testing-library，而那段逻辑**根本不碰 DOM**。
- **那条回收规则是真出过 bug 的**：回滚把流截短之后，基线还停在回滚前那个大数上，于是新到的那句话把总数顶回原值时差值正好是 0 —— 一条回声都收不走，那条灰字永久挂在屏幕末尾（症状：回滚之后再发一句，同一句话在屏幕上出现两次，一次真的、一次灰的）。修过，但**没有任何东西在守着它**。

## 定了什么

把状态机抽成一个**普通对象**：`createPendingEcho()` 返回带 `noteSent` / `dropSent` / `observeStream` / `pending` / `subscribe` 的实例。

- 三个导出函数（`noteSent` / `dropSent` / `observeStream`）和 `usePendingEcho` 都变薄壳，转调**全应用那一份** `appEcho` —— 调用点一行没动。
- `pending(sessionId)` 是那个实例上的普通读取口（hook 的 getSnapshot 也用它），所以测试可以直接喂数据、直接读，不需要 React。
- 那份回收规则的两条（第一次只记基线、条数变少要落基线）现在由测试钉着，拆掉任一条实测会红。

## 还考虑过什么，为什么没选

- **把"待定的那几句"并进流**（由同一条 fold 拥有）→ 那段计数逻辑整体消失。没选是因为它会把**本地乐观状态**混进"服务器事件流的投影"，而那个投影的**纯度**是项目的一条原则：`workspaceWrites` 的注释就写着"同一条流永远算出同一个数，于是断线重连那两次重放算出来的数一样"。混进本地状态之后，同一条流在不同时刻会给出不同的答案。
- **只补测试**（不抽实例）：那要引 jsdom + testing-library 才能碰到那个 hook —— 为了测一个**没有 DOM** 的状态机去引 DOM，方向是反的。
- **把状态放进某个组件**（`WorkspacePage` 或那两个组件之一）：**"发送在飞的时候切走会话、待会儿再切回来"要求那几句回声还在**，而写它的是一个组件、读它的是另一个 —— 挂在任一处，切走就没了，可那条消息其实还在路上。**这就是全应用那一份存在的理由**，不是随手写的全局。
- **顺手加一条 `forget(sessionId)`**：现在没有可观察的后果（会话 id 是 UUID，不会复用），而加清理就多一条"谁负责叫它"的约定 —— 正是这个模块已经在忍着的那类约定。

## 代价与换来的

- 代价：模块大了一点（多一层壳），而全局那一份仍然是全局 —— 这次没有消除它，只是**说清了它为什么必须存在**。
- 代价：那两条**调用顺序**的不变量（`noteSent` 在请求之前、`observeStream` 在 items 更新之后）仍然是注释，不在类型上。它们没有被结构保证，因为把"记回声 + 发请求"合成一个函数就得让这个 lib 里的状态机去认识 HTTP 入口 —— 为了省掉相邻的两行，不值。
- 换来：那条**真出过 bug** 的回收规则第一次有东西守着，而且测它不要 React、不要 DOM。

## 什么情况下该重新考虑

- 真要"待定回声"进流（比如为了让**对面那个人**也立刻看到排队的句子），那就不是这个模块的事了 —— 那要后端在收到请求时就落一条事件，前面那条"并进流"的备选才成立。
- 那份全局表如果哪天真成了内存负担（每条会话一个条目），再加 `forget` 和它的调用点。
