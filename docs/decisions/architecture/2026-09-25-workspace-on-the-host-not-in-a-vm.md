# 决策：工作区放在这台机器上，不搬进虚拟机

## 是什么问题

agent 要跑命令、改文件。这些事发生在**应用所在的这台机器**上，还是放进一台虚拟机（那边有资源限额、可以禁网）？

## 定了什么

工作区就在应用所在的这台机器上（`LocalWorkspaceManager`、`LocalCommandExecutor`）。**代价写在明面上**：命令没有资源限额、没有网络隔离 —— `CommandExecutor` 只给超时和输出截断，别的没有。

## 还考虑过什么，为什么没选

- **工作区在虚拟机、应用留在这边**：那能拿到真的隔离（内存与 CPU 限额、禁网、只读挂载）。没选它是因为：整个项目要讲的是"两个人的 agent 在同一个仓库上怎么协作"，而隔离层会把**命令与工作区之间那条链路**变成一堆跨机器的搬运 —— 我们想展示的东西会被这些管道淹没；而且隔离是**另一个问题**（部署与沙箱），不是这个模型的核心。
- **应用也搬进虚拟机**：那连"两个人在自己的机器上看到实时的过程"这个前提都要重做。

## 代价与换来的

- **没有硬隔离**：一条命令能碰这台机器上的文件和网络，走到哪儿算哪儿（审批只是"问人"，不是"拦住"）。唯一的收窄在环境变量上 —— 凭据形状的名字不递给子进程，见"子进程的环境是重建出来的"那篇。这条和"审批的边界是项目"那篇是同一个代价的两面。
- 换来的是：模型跑的命令就是**用户机器上真实的命令**（构建、测试跑的都是真的），链路短、行为可预期、能讲清。
- 选宿主机还带来一串**平台特有的代价**（都在 Windows 上）：`core.autocrlf` 不关就会让 diff 变成全文改动、路径长度限制、文件被占用导致删不掉 —— 这些都是"跑在用户的机器上"要付的账，也都固化在 git 的硬化参数里。

## 什么情况下该重新考虑

要多租户、或者要把 agent 跑在别人的机器上时 —— 那时隔离是前提，工作区与命令都得进沙箱。
