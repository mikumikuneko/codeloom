# 决策：执行租约自研，fencing 的发号放 MySQL

## 是什么问题

一棵树上同时只能有一个人在跑一轮，这要互斥。但锁会过期、进程会僵住：一个已经失去锁的写入者（网络卡了一下、GC 停顿了几秒）回来接着写，光靠"拿没拿到锁"是挡不住的 —— 锁服务只能拦住"没拿到锁的人"，拦不住"以为自己还持有锁的人"。

## 定了什么

两件事分开做，都是 domain 里的端口加一个实现：

- **租约**（`ExecutionLease` / `LeaseToken`）：Redis `SET NX PX`，key 是 `codeloom:workspace-lock:<workspaceId>`，续租在 TTL 的三分之一处，`renew` 用 Lua 比对 holderId —— 比不中就返回 0，意味着"你已经不是这个锁的主人了"。**每棵树一把**，不是每会话一把。
- **fencing**（`WorkspaceFence`）：MySQL 里的 `fencing_token` 列，每次拿到租约就往前推一格；所有写入在落库前 `assertValid` 一次，token 比库里的小就拒。建会话写第 0 条事件也要 token —— 没有"这条不用记账"的例外。

失去租约之后**一个字都不写，也不释放锁**（那条路本来就是安全空操作，跳过它只是让"这一轮什么都没动"在代码里显式可见）。

## 还考虑过什么，为什么没选

- **用 Redisson 的 `RLock`**：能省掉自己实现的这一层，但它不管 fencing token —— 省了时间，却把这块最要紧的保证留在了外面。（这里有一次自我更正：`RFencedLock` 其实提供 fencing，我当时说"它不做"，是错的。）
- **Redlock**：它要解决的是"让锁服务本身更可靠"，而 fencing 解决的是"锁失效之后，过期持有者的写入被拒绝"，两件事是**正交的**；而且 Redlock 在上游已经被废弃。
- **计数器用 Redis `INCR` 发号**：我们加 fencing 的理由正是"连 Redis 的持久化都不信任"，再用 Redis 发号就自相矛盾。Redis 一旦回退，那条会话会永久写不进去。
- **只靠租约、不要 fencing**：不认真考虑，因为"锁过期 + 写入者醒来"是这类设计里最容易出、也最难查的一类 bug。

## 代价与换来的

- 建一次会话多两次 Redis 往返；每次拿租约多一次 UPDATE。换来的是计数器不可能回退 —— 一个失去执行权的写入者，它的写入**会被存储层拒掉**，而不是靠它自觉。
- 两个中间件都得在（Redis 管互斥、MySQL 管发号）。这是刻意的：它们各自失效时，对方还能顶住。
- **锁和计数器都挂在工作区上，不挂在会话上**（`LeaseToken` 同时带会话 id 和树 id）。反例很具体：同一个人的两条会话**共用一棵树** —— 如果 fencing 值留在会话行上，一条会话拿到的失效 token 在另一条会话的写入路径上会被放行，而它们改的是同一批文件。
- 失去租约之后不释放锁，那棵树要等到 TTL 到期才能被别人拿走 —— 用一段短暂的空窗，换"不误伤别人的锁"。（补一句订正：`release` 的 Lua 会比对 holderId，对不上就返回 0 —— 它本来就是**安全空操作**，不是"会误删别人的锁"。原先有一处注释把这条说反了。）
- **发号必须在抢到锁之后**：反过来做的话，一个抢锁失败的人也会把计数器推过当前持有者，于是活着的那位下一次写入就被自己的守门踢掉 —— 一个纯粹的"顺序"问题，代价却是可用性。
- Redis 的**主从异步复制**同样会丢锁（哨兵不管这件事）：主挂了、从还没收到那条 `SET`，锁就凭空没了。这是"发号不能放 Redis"的另一条理由 —— 锁可以在 Redis，计数器不行。
