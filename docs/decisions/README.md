# 决策记录

这里放**跨文件、有备选、以后有人会问"为什么不那样"**的决定。改个名字、调个间距、某段代码为什么这么写 —— 那些在代码注释里，不放这儿。

## 布局与命名

`{class}/yyyy-mm-dd-主题.md`。日期取**第一次提出**那天，不是最后改完那天。

## 分类

一条决策只归一类，写在顶层目录上。`architecture` 与 `process` 的分界：前者管**上线源码**（模块怎么分、运行时词汇是什么），后者管代码**外面**的工具与流程。分不清时看它改的是"东西本身"还是"围绕它的做法"。

| class | 管什么 |
|---|---|
| `architecture` | 关于上线源码的结构决定 —— 模块怎么分、运行时词汇是什么、各部分的边界在哪 |
| `feature` | 新的能力（用户看得见的、或模型看得见的） |
| `bug-fix` | 修一个缺陷，**或补上一个事后复盘发现的洞** —— 理由值得留下的那些 |
| `simplification` | 删掉代码、行为或界面，没有换来新能力 |
| `process` | 代码**外面**的：工具、检查、规范、协作方式 —— 不是运行时行为 |
| `testing` | 测试基础设施与策略 |

**没有 `refactor` 这一类**：它和 `simplification` 重叠 —— 后者的判据（"可观察的行为变了吗"）已经把它盖住了。判不准的时候，先问这一句。

## 什么时候写一篇

跨文件、**有备选**、以后有人会问"为什么不那样"的决定，写一篇。机械改动、命名、局部界面调整不写。

**写之前先搜一遍这里有没有讲过；有就改那篇，不新开。**

## 文件格式

第一行 `# 决策：<标题>`，然后四段，标题固定：

- `## 是什么问题` —— 当时面对的是什么。**不要写成方案说明书**
- `## 定了什么` —— 现在时，描述现在真实的做法。点符号名用反引号（`EventStore`、`LeaseToken`）
- `## 还考虑过什么，为什么没选` —— **这段是重点**：一条备选一段、粗体开头，紧接着给"**击败它的那条具体理由**"，不是把备选罗列一遍；争议大的单独用 `### 为什么不选 X`。试过之后才放弃的，把实测结果写进去
- `## 代价与换来的` —— 亏了什么、赚了什么

可选一段 `## 什么情况下该重新考虑`，想不出就空着。

## 几条规矩

- **原地改事实，不要追加变更历史**：代码挪了位置、改了名字、换了默认值，就改那几句，不许在末尾追加一段"后来又改成 X 了"。
- **这不是改写决策的许可**：决策本身被推翻，就新写一篇，两篇互相点名 —— 不许把旧那篇改成反的。
- **理由用自己的话总结**：别搬对话里的原话，也别写"某某项目是怎么做的"—— 这篇讲的是**我们**为什么这么定。
- **不链源码文件**：点符号名就够了 —— 链会烂，名字能搜。反过来，代码注释可以指向这里：注释讲"这段为什么这么写"，这里讲"为什么选它、没选谁"。
- 这里**不写状态**：只放已落地的决定。提了没做的留在对话与待办里；被否掉的写进第三段。
