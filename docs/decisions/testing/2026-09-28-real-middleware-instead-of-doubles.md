# 决策：持久化与租约的测试连真中间件，不打桩

## 是什么问题

要验"这条事件真的写进去了、这个租约真的抢不到"，是拿内存替身演一遍，还是连真的 MySQL 和 Redis？

## 定了什么

事件存储、租约、事件总线这些测试连**真的中间件**；连不上就**跳过**（不是静默通过，也不是假装成功）。测试自己建数据、自己清数据。

## 还考虑过什么，为什么没选

- **内存替身 / fake**：我们最想验的恰恰是"真存储的行为" —— fencing token 的比较、`RPOPLPUSH` 的原子性、Redis 重连之后计数器的走向。换成替身，这些就变成**我们自己写的另一版假逻辑**，被测的变成了它，真问题照样在。
- **用 H2 之类的替代库**：SQL 方言与事务行为都不一样，尤其是那些跟"并发写同一行"有关的断言。
- **连不上就当失败**：会把"这台机器没起中间件"和"代码坏了"混成同一件事，于是没人愿意在本地跑。

## 代价与换来的

- 跑测试的机器上要有这两个中间件；测试比纯内存的慢；还要处理"上次跑剩的数据"（所以有可用性检查与清理）。
- 换来的是：断言打在真行为上，而且"没跑"是有信号的（跳过），不会变成一次假绿。
